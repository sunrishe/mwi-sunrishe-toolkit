# 工程结构与开发规范

本文档用于指导后续开发时“文件放哪里、模块怎么拆、构建怎么接、验证怎么做”。当前待办见 `docs/待办与状态.md`，长期业务规则见 `docs/业务功能要求.md`。

## 一、工程目标

- MST 发布产物固定为单个油猴脚本 `dist/mst.script.user.js`，另有一份只含油猴头部的元数据文件 `dist/mst.script.meta.js`。
- 开发产物为 `dist/mst.script.dev.user.js` 与对应的 `dist/mst.script.dev.meta.js`，通过 `yarn watch` 持续生成。
- 源码使用 ES Module，由 Rollup 打成单个 IIFE，不拆分为多个本地 `@require` 包。
- 目录优先表达用户功能，避免按类、函数或 `state/view/events/controller` 机械细拆。

## 二、目录结构

```text
src/
├─ index.js                       # 极简启动入口
├─ app/
│  ├─ main.js                    # 创建上下文并安装公共层、业务模块
│  └─ app-controller.js          # 站点启动、顶层控制器和运行实例
├─ common/
│  ├─ build-flags.js             # dev/prod 构建开关
│  ├─ constants.js               # 跨模块公共常量
│  ├─ data.js                    # DataHub、缓存和 WebSocket 数据入口
│  ├─ i18n.js                    # 语言服务
│  ├─ market.js                  # 跨模块市场能力
│  ├─ messages.js                # 统一中英文文案
│  ├─ runtime.js                 # 运行时工具和页面适配器
│  ├─ ui.js                      # 模板、弹窗、Toast 等公共 UI
│  └─ styles/                    # 全局公共 CSS
└─ modules/
   ├─ index.js                   # 业务模块装配器
   ├─ ability-upgrade/
   ├─ character-card/
   ├─ combat-upgrade/
   ├─ dungeon-profit/
   ├─ eds-milkonomy/
   ├─ equipment-comparison/
   ├─ house-calculator/
   └─ toolkit-menu/
```

其他顶层目录：

| `dist/`                      | Rollup 构建产物；正式包由命令生成，开发和调试包不提交                                                       |

## 三、文件归位

| 新增内容                   | 推荐位置                           | 说明                                             |
| -------------------------- | ---------------------------------- | ------------------------------------------------ |
| 应用启动、站点初始化       | `src/app/`                         | 只做顶层装配，不承载完整业务功能                 |
| 新用户功能                 | `src/modules/功能名/index.js`      | 一个用户功能对应一个目录                         |
| 模块私有计算或数据         | `src/modules/功能名/`              | 与 `index.js` 同目录，不提升为公共层             |
| 两个以上模块真实复用的能力 | `src/common/`                      | 不为“以后可能复用”提前抽象                       |
| 统一 i18n 文案             | `src/common/messages.js`           | 不保留散落的 `isZH` 文案分支                     |
| 全局公共 CSS               | `src/common/styles/*.css`          | 由 raw CSS 插件作为字符串打入产物                |
| 跨模块共用组件 CSS         | `src/common/styles/components.css` | 多个模块复用的同一组件只写一份，类名不带模块前缀 |
| 模块私有 CSS               | `src/modules/功能名/styles.css`    | 与使用它的业务模块放在一起                       |
| 带运行时变量的动态样式值   | 模块 `index.js`                    | JS 只设置 `--mst-*` CSS Variables                |
| 测试                       | `tests/*.test.js`                  | 文件名与功能或公共能力对应                       |
| 用户说明                   | `docs/usage.md`                    | 面向使用者，不写技术流水账                       |
| 更新日志                   | `docs/changelog.md`                | 用户可感知的版本变化，按模块合并，只写中文       |
| 当前状态                   | `docs/待办与状态.md`               | 只保留进行中版本、待办和版本号状态               |
| 历史版本记录               | `docs/archive/`                    | 已发布版本的验收与实现记录，按版本倒序           |
| 长期业务规则               | `docs/业务功能要求.md`             | 数据、功能、UI 和兼容要求                        |
| 算法或链路分析             | `docs/analysis/`                   | 公式、来源、限制、专项结论和功能回归清单         |
| 外部数据、旧脚本、备份     | `references/` 对应子目录           | 运行时代码不得读取                               |
| 运行时第三方静态依赖       | `vendor/` 对应子目录               | 仅放必须通过仓库地址加载的文件                   |

任务产生的一次性迁移脚本和临时文件必须在任务结束前删除。

## 四、模块拆分

### 4.1 默认规则

1. 每个用户功能建立一个 `src/modules/功能名/` 目录。
2. 模块默认只保留一个主要业务文件 `index.js`，相关状态、事件和 UI 放在一起，优先保证阅读连续性。
3. 不按函数数量、类数量或代码行数机械拆文件；文件较长不等于职责混乱。
4. `src/modules/index.js` 只负责创建模块并挂载到 `ctx`，不写业务实现。
5. `src/app/` 只负责站点启动和顶层生命周期，不吸收模块内部逻辑。

### 4.2 可以单独成文件的边界

只有出现以下真实边界时才拆分：

- 可独立测试、基本不依赖 DOM 的纯计算，例如 `calculator.js`、`planner.js`。
- Worker 运行入口，例如 `worker-runtime.js`。
- 图片或文件导出等独立技术链路，例如 `exporter.js`。
- 大块稳定常量、预设或数据适配逻辑，例如 `constants.js`、`presets.js`、`data.js`。
- 大块渲染或动态样式，且从主体移出后能明显降低理解成本。

禁止仅为了“看起来模块化”创建只有少量转发代码的 `state.js`、`view.js`、`events.js`、`controller.js`。

### 4.3 依赖方向

- `src/index.js -> src/app/`
- `src/app/ -> src/common/ + src/modules/`
- `src/modules/ -> src/common/`
- 纯计算文件不反向依赖 DOM、弹窗或应用控制器。
- 模块之间不要直接形成循环依赖；确需协作时由 `ctx` 或应用层装配。

## 五、构建与环境开关

- 项目使用 Yarn Classic `1.22.22` 管理依赖，版本声明位于 `package.json#packageManager`。
- 依赖安装使用 `yarn install`，只维护 `yarn.lock`，不得同时保留 `package-lock.json`。
- `userscript-header.txt` 维护油猴头部，版本由 Rollup 从 `package.json` 注入。
- 每次构建除 `.user.js` 外还输出同名不同后缀的 `.meta.js`（prod 为 `dist/mst.script.meta.js`，dev 为 `dist/mst.script.dev.meta.js`）：内容就是 `.user.js` 开头那段油猴头部，只含元数据不含代码，供检查更新这类只读 `@version` 的场景下载；头部同样由 `userscript-header.txt` 加版本注入生成，不允许另写一份版本号或单独维护 meta 内容。安装地址按后缀替换推导（`.meta.js` → `.user.js`）的规则对这两个产物同样成立。
- `yarn build` 会先执行 `lint:fix` 和 `format`，再生成正式包；`yarn build:dev` 保持轻量，只生成带时间戳版本的开发包。
- `yarn watch` 监听 `src/**`、油猴头部和 Rollup 配置并持续构建开发包。
- `yarn watch:server` 在监听开发包的同时启动本地 HTTP 服务，并刷新 `dist/MST-local-debug.user.js` 与 `dist/MST-http-debug.user.js`；前者通过 `file:///` 引入本地 dev 包，后者通过本地 HTTP 引入 dev 包并追加更新时间戳。本地文件版需要浏览器允许油猴扩展访问本地文件。
- dev/watch 构建保留调试可读输出；prod 构建将内嵌 CSS 输出为每条规则一行的紧凑格式，不对 JS 做 esbuild 压缩或语法收紧。
- dev/prod 差异统一定义在 `src/common/build-flags.js`，业务代码只读取 `BUILD_FLAGS` 或由其生成的配置。
- 开发包可以展示语言切换等调试入口；正式包不得展示开发专用按钮和信息。
- Rollup raw CSS 插件读取 `.css` 并转成字符串模块，CSS 不单独成文件，始终内嵌在 `.user.js` 里（`.meta.js` 只含头部，不带样式和代码）。
- 除非用户明确要求，不新增运行时远程依赖；新增时必须先说明来源、用途和油猴权限影响。

## 六、代码规范

- 文档和关键注释使用中文，变量、函数和 API 使用清晰的英文语义命名。
- 编辑器基础格式遵循 `.editorconfig`：UTF-8、LF、2 空格缩进、文件末尾保留换行并清理无效行尾空格。
- JS、CSS、JSON 和 Markdown 排版遵循 `.prettierrc`：120 列、单引号、分号、对象括号内空格且不保留尾逗号。
- `.gitattributes` 固定文本文件使用 LF；不得依赖个人编辑器或 Git 的换行符设置。
- VS Code 使用项目推荐的 EditorConfig、Prettier 和 ESLint 插件；JetBrains IDE 使用项目 Prettier 和 EditorConfig 配置。
- DOM `id` 和 `class` 使用 `mst-模块名-` 前缀，自定义事件使用 `mst:` 前缀。
- 跨模块复用的同一组件用**不带模块前缀**的共用类名，样式集中写在 `src/common/styles/components.css`，模块只在自身根类下写布局差异：同一组件被复制成多套模块前缀类名时会各写一份样式，改一处漏一处。共用类名格式为 `mst-<组件名>-元素`，组件名取语义名（如 `mst-help-*`、`mst-picker-*`、`mst-item-*`），不写模块名；数值涨跌色这类跨模块语义色同样共用（`mst-positive` / `mst-negative` / `mst-neutral`）。
- 同一个组件内样式相同但功能不同的按钮（如名片的下载 / 复制 / 重置）保留各自的语义类名，样式用一条共用选择器列表声明即可，不额外抽基类类名；只有需要新增的公共样式钩子才落到 `components.css`。
- localStorage 键使用 `MST_简短模块名_key` 格式。
- 游戏公共数据优先来自 WebSocket `init_client_data`；启动缓存优先通过官方 `window.localStorageUtil.getInitClientData()` 读取，角色数据来自 `init_character_data` 和后续 WebSocket 更新。
- 页面功能必须做站点隔离，不在无关站点初始化观察器、定时器、缓存或 UI。游戏只有**正式服**与**测试服**两个运行环境：`hostname` 以 `test.` 开头为测试服，`milkywayidle.com` 与 `milkywayidlecn.com` 及其 www/裸域都是正式服（cn 是正式服的中国官方镜像入口，与 .com 是同一环境的两个入口，不是独立服务器）；环境判定统一用 `CONFIG.isTestServer`，不得新增「国服/中文站」这类第三环境分支（规则细节见 `docs/业务功能要求.md` §站点隔离）。
- 使用 uhtml 模板渲染列表时，数组插值必须保持扁平：节标题等标记元素与数据行数组要展开进同一层数组，不能把数组直接嵌进数组插值（否则 Fragment 锚点失效导致整体渲染失败）。
- uhtml 数组插值里不能出现 `null` / `undefined` 元素：数组位会抛 `Cannot read properties of null`；条件渲染要用空模板或空数组，或只收集命中项。
- SVG 片段必须用 `TemplateRenderer.svg` 生成，不能用 `TemplateRenderer.html`：`html` 标记生成的元素带 HTML 命名空间，插进 `<svg>` 后不显示且控制台不报错，只能靠截图发现。
- uhtml 插槽值（`${...}`）必须是**单一根节点**的模板：多个同级兄弟节点会被渲染成空内容且控制台不报错，只能靠浏览器验证发现；需要并列多块内容时先包一层容器元素。
- 条件渲染不要用「空模板 ↔ 真实模板」互相替换：`TemplateRenderer.render` 按模板身份缓存插槽，从空模板（`TemplateRenderer.html` 的空模板）换成真实模板时会在补丁替换阶段抛 `replaceWith is not a function`；容器常驻、用 `.hidden` 开关（配套写 `[hidden] { display: none }`，避免被 `display: flex` 覆盖）。
- 模块帮助浮层（`CalculatorHelpPopover`）是跨模块共用组件：类名固定 `mst-help-anchor` / `mst-help-trigger` / `mst-help-popover*`，样式统一在 `src/common/styles/components.css`，挂载时不再传 `moduleName`；新模块直接挂 `CalculatorHelpPopover` 即可，不需要补任何样式。浮层 `id` 用递增序号保证多弹窗不重号。
- 渲染和交互路径不做重复的重计算：列表候选、索引这类可复用结果按数据签名缓存，模拟、导出等重计算只在用户请求时构造输入，不在每次渲染里重建。
- 修改既有代码时只处理当前需求，不顺手重构相邻模块。

## 七、测试和质量门禁

常用命令：

```powershell
yarn lint
yarn format
yarn format:check
yarn build:prepare
yarn test
yarn build:dev
yarn watch:server
yarn build
yarn run check
```

`yarn build:prepare` 依次执行 `lint:fix` 和 `format`。`yarn run check` 先执行同一套源码修复，再执行 Node 测试、dev 打包和 prod 打包，避免重复修复。Yarn Classic 自带同名 `yarn check`，调用项目脚本时不得省略 `run`。Husky 的 `pre-commit` 通过 lint-staged 检查暂存文件。

验证按风险分级：

- 仅文档、注释、错别字或极小且明显低风险的改动可以不验证，交付时说明未执行验证。
- 单一模块的一般改动至少运行直接相关的 lint、测试或构建。
- 涉及多个文件、多个模块、公共能力、依赖或构建流程时执行完整 `yarn run check`。
- 使用 Playwright MCP 前必须先阅读 `docs/analysis/Playwright MCP 使用规范.md`，在 MCP 服务列表中按“Playwright”关键字找到 Playwright MCP 服务器并确认其 `browser_*` 工具；工具名前缀随客户端变化，不得按 `mcp__playwright__` 前缀查找。
- 改动范围较大，或涉及 UI、DOM、CSS、交互流程、站点兼容时，必须在自动检查之外使用 Playwright MCP 服务打开实际目标页面，验证核心流程、页面显示、重复操作和控制台错误。
- 只调整观感、不改变交互流程与 DOM 结构的样式微调（页签顺序、间距、配色、字号、排版位置等）不需要浏览器验证：执行相关测试与 `yarn run check` 即可交付，并在交付说明里写明未做浏览器验证。
- “Playwright MCP”指在 MCP 服务列表中按“Playwright”关键字找到的官方 Playwright MCP 服务器及其 `browser_*` 工具，识别依据是工具功能名而不是前缀（前缀由客户端决定）。Browser plugin / Browser skill 内置 Playwright、Node REPL 浏览器控制和 `playwright-cli` 不属于本项目认可的 Playwright MCP 验证。
- 交付前优先执行 `yarn run check`（源码修复、测试、dev 与 prod 打包），受环境限制无法执行时说明原因。
- 本地预览、静态 Mock 或测试夹具的结果必须单独标记为补充验证，不得写成实际目标页面已通过。
- 因登录状态、外部服务或环境限制无法完成浏览器验证时，必须记录原因和未覆盖风险，不得默认标记为通过。
- 浏览器验证的交付记录按 `docs/analysis/Playwright MCP 使用规范.md` §五 的格式写清实际页面或补充验证、视口、关键交互、控制台结果和未覆盖风险。

以下改动必须补充或更新测试：

- 修复 bug 或修改业务计算公式。
- 修改 DOM 插入、事件绑定或观察器逻辑。
- 修改 dev/prod 构建开关。
- 修改数据来源、缓存、跨站同步或 Worker 协议。
- 调整目录和模块边界时，测试不得继续读取已废弃路径。

UI 改动除自动测试外，还应在游戏页面检查重复插入、语言切换、窄屏布局、弹窗滚动和站点隔离。

## 八、文档维护

- `package.json#version` 是正式版本号的唯一来源，版本遵循 SemVer：不兼容变更提升 major，向后兼容的新功能提升 minor，修复和兼容性调整提升 patch。
- 功能或用户可见行为变化必须提升版本号；仅文档、注释、格式、测试或不影响产物行为的工程配置可以不提升。
- 提升版本号时同步更新 `docs/changelog.md` 更新日志和 `docs/待办与状态.md` 当前版本；`userscript-header.txt` 的版本由 Rollup 自动注入，不手工重复维护。
- 用户可见功能变化更新 `docs/usage.md` 使用说明和 `docs/changelog.md` 更新日志。
- `docs/usage.md` 是对外的油猴插件页说明（中英双语），每个功能只写“做什么”，保持一两句话；入口、关键限制写在同一节内，不写仓库路径、内部文档引用、实现细节、参数清单或界面字段描述。
- `docs/changelog.md` 更新日志只写用户可感知的功能变化，**条目按模块合并**（同一模块的改动合并为一条，一条里可并列同一模块的几件事；不按开发过程或改动次数拆成多条，也不逐个功能分行罗列），从用户角度描述（说清哪个功能变了、用户能做什么），简短直接；只写中文（脚本名、专有名词除外），不写英文句子，不写实现细节与机制解释；不记录开发过程中的问题修复和版本规划中间态，涉及实现约束的结论记入 `docs/业务功能要求.md` 或对应规范文档；多个版本的内容统一规划到一个版本号时，只保留规划后的版本条目，正文不做版本整理表述，多版本内容用“收录”“统一规划”等措辞。
- 临时文件与本地调试产物（`*.tmp`、`*.bak`、`*.orig`、`*.rej`、`dist/MST-*-debug.user.js` 等）不得提交；交付前清理工程内和任务过程中产生的临时文件，确认暂存区无临时文件，不删除历史备份和专项参考资料。
- 当前任务和版本状态更新 `docs/待办与状态.md`，该文档只保留进行中版本、待办和版本号状态。

## 九、AI 开发清单

1. 阅读 `AGENTS.md`、本文档和任务相关业务文档。
2. 明确目标、假设和可验证的成功标准。
3. 搜索现有实现，优先沿用已有模块和公共能力。
4. 按用户功能聚合代码，只在真实边界拆文件。
5. 按 SemVer 判断是否提升版本，并同步相应文档。
6. 按风险分级完成相关检查；使用 Playwright MCP 前先阅读 `docs/analysis/Playwright MCP 使用规范.md`，较大改动增加浏览器实际验证。
7. 清理本次任务产生的旧实现、临时脚本和无效文档。
8. 总结改动、版本、验证结果和剩余风险。
