# 业务功能要求

本文沉淀 MST 长期有效的业务规则和功能约束。当前待办和状态见 `docs/待办与状态.md`；工程结构、文件归位、模块拆分和验证规则见 `docs/工程结构与开发规范.md`。

## 一、项目定位

- 脚本名称：MWI Sunrishe Toolkit，简称 MST。
- 当前源码入口：`src/index.js`。
- 正式构建产物：`dist/mst.script.user.js`。
- 开发构建产物：`dist/mst.script.dev.user.js`，油猴本地开发引导优先引用该文件。
- 地下城加入前的备份：`references/legacy-scripts/mst/mst.script.pre-dungeon.user.js`。
- 历史基准脚本：`references/legacy-scripts/mst/`。
- 运行时第三方静态文件：`vendor/uhtml/uhtml.iife.min.js`，由油猴头部通过仓库固定版本 `@require` 加载。
- 用户文档：`docs/usage.md`（中英双语使用说明）；更新日志：`docs/changelog.md`（只写中文）；历史版本记录：`docs/archive/版本验收记录.md`。
- 专项分析文档：
  - `docs/analysis/地下城收益计算链路分析.md`
  - `docs/analysis/装备提升模拟基准说明.md`

## 二、通用业务约束

### 修改原则

- 只修改当前需求直接涉及的代码，不顺手重构无关区域。
- 不简化、不改写原脚本既有业务逻辑；迁移功能时先保证行为一致，再讨论优化。
- 不编造游戏接口、数据结构或原脚本逻辑，优先核对游戏源码、官方数据和来源脚本。
- 修复过的问题必须增加测试用例，避免重复回归。
- 删除因本次修改产生的无用代码；原本存在但与任务无关的代码不随意清理。

### 数据来源

- 游戏公共数据优先来自运行时 `init_client_data`。
- 角色动态数据优先来自运行时 `init_character_data`、`profile_shared` 及后续相关增量更新。
- 市场价格统一按有效正数取值：`a/p/b`（左一、最近成交、右一）中取第一个有效正数，缺价哨兵 `0`/`-1` 视为缺价，全缺时才回退官方市场价值或按 `0` 处理。
- `references/` 中的数据只用于开发核对和测试，不作为运行时数据源。
- SVG 路径优先从游戏已经加载的资源映射获取，保证游戏更新后能取得最新文件名；只保留与游戏当前默认路径一致的兜底。

### 站点隔离

- 游戏功能只在银河奶牛放置正式服、测试服和国服游戏页面初始化。
- 老利润网 `https://milkonomy.pages.dev/` 与新利润网 `https://hyhfish.github.io/milkonomy/` 只初始化利润网同步功能。
- 战斗模拟器 `https://aiwwb.github.io/milkywayidle_battle/` 只初始化战斗模拟导入功能。
- 每个功能先判断站点和页面环境，不在无关网站创建观察器、定时器、缓存或 UI。

## 三、数据与缓存要求

### init_client_data

- WebSocket 推送的 `init_client_data` 是实时数据来源，收到后更新 MST 内存数据。
- 页面启动时优先调用游戏官方 `window.localStorageUtil.getInitClientData()` 读取基础数据缓存；`document-start` 阶段官方对象尚未挂载时，允许直接读取并解压游戏的 `initClientData` 缓存作为兼容兜底。
- 不为 MST 额外持久化 `init_client_data`。
- 脚本内部通过统一 DataHub/Service 读取原始结构和按需索引。
- `GAME_DATA` 不再作为主要数据源；可从官方 client data 获取的数据必须优先使用官方数据。
- 名称和翻译参考 `mwi-helper.js` 的 `staticInit` 思路，从游戏 i18n 资源读取。

### WebSocket 页面桥

- 页面桥只做转发、不改原型：注入构造器用 `Proxy` 的 `construct` 陷阱把 `new.target` 原样交给下层构造器（`Reflect.construct`），`window.WebSocket.prototype` 与新建实例的原型必须与“工具箱未安装时”完全一致。
- 不得用普通函数替换构造器（即使借用原生原型）：函数体内建出的实例会丢弃 `new.target`，后装脚本 `class extends` 时派生类原型不在实例链上，它的原型补丁与 `instanceof` 判断都会静默失效。
- 采集不依赖桥在包装链中的位置：只要游戏创建 socket 经过桥的陷阱，`mst:ws:message-raw`/`send-raw`/`state-raw` 就必须照常派发；把 `window.WebSocket` 整体替换为不调用前一个构造器的假对象不在适配范围内。
- 其它脚本彼此之间造成的原型链断裂不属于本桥职责：桥不做 `setPrototypeOf` 之类的补救，只保证自身既不失效、也不制造新的失效。

### 角色数据

- 统一捕获并维护 `init_character_data`、`profile_shared` 及后续相关增量更新。
- `profile_shared` 允许写入 localStorage 长期缓存，并设置合理有效期；内存数据与有效缓存合并后供名片使用。
- 角色缓存使用对象结构，以 `characterId` 为 key。
- 数据更新时间属于具体角色，切换名片角色时必须同步切换。
- 战斗等级、技能等级、装备、工具、房屋等增量变化统一更新 DataHub，供所有模块复用。
- `new_battle`、`battle_updated`、`battle_unit_fetched` 等战斗流水消息不得进入通用角色数据更新链，不得调用 `updateCharacterData` 或 `applyCharacterMessage` 反写 DataHub 角色状态。
- 战斗开始后配装方案、装备、技能、房屋、Buff 等战斗模型均视为官方战斗快照；该快照只用于战斗内展示或计算，不能污染名片、配装名片、装备对比等通用角色数据。
- 如需读取当前战斗地图、持续时间、经验或掉落，只能建立独立的战斗运行时缓存，例如 `combatRuntime`；该缓存与 `characterData.raw` 完全隔离，且只供明确需要当前战斗状态的模块使用。
- 当前战斗地图可从 `characterActions[0]` 或 `partyInfo.party` 的 `actionHrid`、`difficultyTier` 结合官方 `actionDetailMap` 获取；普通星球战斗和地下城均按官方 `combatZoneInfo` 判断。
- 当前战斗持续时间优先来自官方 React `GamePage` state 中的 `combatStartTime`；本次战斗累计经验优先读取 `battlePlayers` 当前玩家单位的 `totalSkillExperienceMap` 与 `totalAbilityExperienceMap`，也可通过官方 WS `view_battle_unit` / `battle_unit_fetched` 按需补齐；不能假设 `battle_updated` 会持续推送经验累计。

### 存储与 GM API

- 游戏站普通功能优先使用内存和 localStorage，不使用 GM API 随意持久化。
- EDS 配装同步属于跨域通信，保留 `GM_setValue`、`GM_getValue`、`GM_addValueChangeListener` 等原有链路。
- 游戏站写入配装信息到 GM，利润网站监听变化并读取最新数据；必须与 EDS 原逻辑一致。
- 战斗模拟导入同属跨站通信：游戏站在 `MST_SIM_*` 键下维护角色快照、客户端字典裁剪版与战斗快照，队友资料不单独维护一套裁剪数据，而是镜像名片缓存（`MST_CC_profiles` 对应的 DataHub 内存态 `characterData.profiles`）写入 `MST_SIM_profiles`，条目结构与名片缓存一致；模拟器站只读；测试服（`test.*` 域名）一律不写入，避免正式服与测试服快照互相覆盖。
- 剪贴板导入购物车和房屋材料加入购物车必须调用 MWITools 公开的购物车接口（`window.MWITools.shopping`），不自行伪造其存储结构。
- 只有检测到 MWITools 注入的公开 window 属性（`MWITools.shopping`）时，才显示相关按钮。

### 订阅通知

- 只在游戏页面打开期间监听队列变化，离线期间不感知、不补推；正式服、国服、测试服统一由订阅总开关控制，测试服页面的通知必须带“测试服”标识与角色名。
- 队列变动以官方 `CharacterAction.id` 判定：同 `id` 的 `action_completed`（多步任务进行中）不推送；当前任务以 `isDone` 结束且队首变化才推送完成通知，队列腾空附加提醒；有限次数任务未达上限被移除按取消处理——不报完成，但队首接上的新任务仍按任务开始通知播报；长时间未完成任务按周期推送进度（默认 30 分钟，可调或关闭）。
- 任务开始通知：**队首换成另一个任务即推送**，来源包括完成切换、被其他任务顶掉、被挤下去的任务重新回到队首、取消切换、空队列入队；只按队首变化判定，不区分行动类型（迷宫、个人战斗同样适用，且这些行动被顶掉再回来时自身 `id` 不变也照样推送）。同一任务一直在队首连续执行（迷宫跑不同房间/环节、战斗打不同波次）不推送——队首 `id` 未变即无事件。**组队/战斗行动（`partyID` 非 0）例外**：它们改由"真正开战"播报，队首变化时不推送，避免队伍还没准备就绪就报一条、开战时再报一条内容重复的通知；判定依据是 "是否拿到过队伍状态"，一旦拿不到队伍状态（游戏侧不再提供 `partyInfo.party.status`）就退回队首变化播报，保证不至于一条都收不到。
- 组队战斗开战播报：`party_updated` 的 `partyInfo.party.status` 进入 `battling` 时推送一条任务开始通知（官方 `PartyStatus`：creating/recruiting/battling/disbanded，进入 `battling` 时队首 `id` 未变、官方自己也会发"队伍开战"通知），即"准备就绪并过了等待期"的官方信号；战斗结束退出 `battling`、下一轮再进入则再推一条，每次开战各一条。基线（`init_character_data`）里正在开战只记录不推送。
- 任务开始通知内容（与完成行同属一条消息时）：开始行 + 「等待队列」概览 + 时间行 + 角色名行。队列概览与完成/进度通知同口径：不含队首、最多 3 项、超出以 `…共 N 项` 收尾；每项带已完成/总次数，已执行过、轮到会接着做下去的任务由非零次数直接体现，不另列「继续执行」段。
- 消息类型开关：任务开始、任务完成、队列为空、定期进度四个复选框（设置弹窗按此顺序排列）各自独立控制，默认全开，旧配置缺字段视为开启；关闭后不推送对应类型，但进度计时与队列基线仍正常维护（重新开启时口径正确）。**一次队首变化只发一条消息**：上个任务结束与下个任务开始发生在同一次切换里，两个开关分别决定这一条里出现完成行、开始行（都关则不推送）。
- 通知里的行动名按官方 `getActionDisplayName` 口径组装：炼金类（点金、分解、转化、解精炼）为「行动名: 物品名」，强化为「物品名 +<等级>」，其余行动直接用行动名（采集/制作类的 `actionHrid` 本身按物品命名）；物品取自 `CharacterAction.primaryItemHash`（`characterId::itemLocationHrid::itemHrid::enhancementLevel`），解析不到时退回行动名。
- 通知中的队列概览只列等待执行的任务（排除正在执行的队首），最多 3 项；进度与完成通知同口径。队列排序与官方一致：partyID 非 0（组队/战斗行动）在前、个人行动在后、组内按 ordinal 升序；战斗任务名称带官方同款 ` (T<tier>)` 难度后缀（difficultyTier >= 1），进度通知的行动名同样带该后缀。
- 组队战斗行动（partyID 非 0）在同一条 `CharacterAction` 上持续累加 `currentCount`，取消准备再重新准备不更换 id、也没有 `actions_updated`/`action_completed`：模块监听 `party_updated`（`partyInfo.partySlotMap` 按 `characterID` 匹配本方槽位），本方角色从未准备变为已准备（取消准备后再准备、战后再次准备）视为新的战斗会话——进度通知的“已完成次数”从重新准备时重新起算（会话内增量），进度计时同步重置。任务切换、页面加载/重连基线重建后恢复原始累计口径；基线建立时已处于准备状态不算重新准备，取消准备与他人准备变化不重置。
- 会话监控在公共层做：`WebSocketService` 的页面桥监听游戏 WebSocket `open`/`close`，经 `mst:ws:state-raw` 转发为公共事件 `mst:ws:state`（`{state, url}`），模块按需订阅。订阅通知断连（网络断开或同账号被其他登录挤掉，页面不再收到队列消息）期间暂停进度与空队列定时推送，避免用断连前的陈旧队列数据推送（多开页面时表现为同一任务收到两条数据差异很大的进度通知）；收到 `init_character_data`（重连成功重建基线）或 WS `open` 即恢复。页内切换角色（官方 SPA 路由，页面不刷新）同样走该链路：官方 `getConnection` 发现 `characterId` 变化会先关闭旧连接再以新 id 重连，旧连接 `close` 触发暂停、新角色 `init_character_data` 触发恢复并重读配置。
- 渠道凭据与签名口径：钉钉 `oapi.dingtalk.com`（加签 key=secret、毫秒时间戳、Base64 后 URL Encode 追加 URL）；企业微信 `qyapi.weixin.qq.com`（无签名，key 在 URL）；飞书 `open.feishu.cn`（签名 key="{秒时间戳}\n{secret}"、消息体为空，放 `X-Lark-Request-*` 请求头；Hook 地址支持完整地址或仅填 hook-id）。签名口径以官方文档为准，不参考示例 shell 脚本的简化写法。
- 推送统一走 `GmApi.xmlHttpRequest`，头部 `@connect` 必须包含三个渠道域名且不得删减；发送失败按 1/2/4 分钟退避重试最多 3 次，重试耗尽后丢弃；两层频控同时生效——“最小推送间隔”（默认 5 秒，间隔内多次触发合并为最新内容）与“每分钟推送上限”（滑动 60 秒窗口，切换渠道按官方限流带出默认：钉钉/企微 20、飞书 100，可改）。
- 队列跟踪与推送分离：订阅开关关闭期间仍合并官方增量维护队列基线（只跟踪不推送、不补推），重新开启后按当前队列继续，进度与空队列计时从开启时刻重新起算。只有全量基线（`init_character_data`）才算建立队列数据，增量消息不构成基线。
- 定时推送（定期进度、队列为空提醒）要求会话可信，`isSessionTrustworthy` 三条同时成立才跑，任一不满足即暂停、恢复后自动继续：① **页面判据（主）**——游戏判定掉线时会把整块游戏 UI 换成连接提示面板，页头的角色信息块（右上角头像所在块，`GameUiAdapter.query('headerCharacterInfo')`）随之消失，取不到即按掉线处理；实测断线页面上该块与 `[class*="FullAvatar_"]` 数量均为 0，而页头外壳 `Header_header__` 仍为 1，**不能用页头容器判定**；② 没有观测到 WebSocket `close`（被挤掉/断网时游戏立刻断开重连，事件比 UI 更早）；③ 会话没有长时间静默——在线时游戏每 10 分钟发一次 ping、服务端回 pong（游戏源码 `setInterval(this.sendPing, 6e5)`），超过 11 分钟收不到任何游戏消息说明连接已死但游戏自己还没察觉（半开连接）。另外队列为空提醒还要求已经拿到过全量基线——未拿到基线时队列为空只代表“没有数据”，不推送提醒，避免未登录或掉线状态打开的页面每分钟误推一条“行动队列已空”。完成通知不受此限制（事件本身来自游戏消息）。
- 通知末尾角色名行：角色名优先；名称不可用但已有角色 id 时显示「角色 <id>」（用于区分同站多账号，不再输出没有信息量的占位符）；两者都没有时显示「未知角色」——该状态没有队列基线、定时推送已被拦截，正常只会出现在手动测试发送。测试服页面在上述内容后追加 ` · 测试服` 标识。
- 存储边界：只有订阅与渠道配置持久化（`STORAGE_KEYS.SUBSCRIBE_NOTIFICATION`）；当前行动 `id` 基线、计时器、发送队列、最近失败原因一律只存内存，页面刷新/关闭即丢弃重建；不保存队列快照、变动历史或已发通知记录。

## 四、UI 与交互要求

### 弹窗和提示

- 游戏内弹窗、确认和提示统一使用 SweetAlert2。
- 非 Toast 弹窗均支持鼠标和触摸拖动，且不能拖出可视窗口。
- 弹窗高度自动，使用 `svh` 等移动端友好单位限制最大高度；内容超出时只滚动内容区。
- 多行输入框禁止拖动改变大小。
- Toast 与普通弹窗互不影响，Toast 最多同时显示 3 个。
- 普通弹窗层级低于 MWITools 购物车按钮层；Toast 不受该限制。
- 弹窗层级统一由 `src/common/styles/app-base.css` 的 `:root` 变量声明：`--mst-z-popup` 为普通弹窗层级（当前 1000，高于游戏原生 UI 最高 z-index 9、低于 MWITools 购物车把手/抽屉 1001/1002），`--mst-z-toast` 为 Toast 层级（当前 2147483550）。MWITools 购物车宿主在市场导航会话时整体抬到 z-index 2147482000，仍高于普通弹窗。MWITools 更新后必须按此约定重新核对购物车按钮层级并同步本文件与 `app-base.css` 中的取值。
- 弹窗主题内嵌脚本并贴合游戏字体、字号、颜色、间距和布局，不使用 SweetAlert2 默认图标。
- 提示信息使用标题后的问号入口；桌面端悬浮可见，移动端点击也可打开。

### 响应式和样式

- 风格以游戏网站现有组件为准，不制作与游戏割裂的控件。
- 外围按钮、提示文字等使用 `rem` 并兼容移动端。
- 固定格式区域设置稳定尺寸，动态文本不得推动或挤坏布局。
- 长英文允许换行和按单词添加连字符，不能用省略号隐藏关键信息。
- 图标、文字、复选框和表头内容保持水平、垂直对齐。
- 不出现无意义横向滚动条；内容区滚动不能带动弹窗操作区横向移动。

### 国际化

- 所有模块使用统一 i18n，不保留散落的 `isZH` 分支。
- 优先采用游戏网站官方中文和英文翻译。
- 语言跟随当前页面；页面语言变化时，已打开的工具应即时更新文案并保留输入状态。
- 老利润网和新利润网分别读取各自页面语言，不假设两者实现相同。
- 测试用语言切换按钮由 `src/common/build-flags.js` 的 `BUILD_FLAGS.showLanguageToggle` 控制，开发构建显示，正式构建不显示，用户文档不作为正式功能宣传。

## 五、功能要求

### 工具箱入口

- 工具箱只在游戏页面初始化，利润网站不显示游戏工具箱。
- 顶部角色信息区域显示 `工具箱/Toolkit` 按钮，点击后打开挂在该区域下方的 MST 工具箱下拉层；点击右上角头像弹出的原生菜单最前面同样显示 `Sunrishe 工具箱` 入口，点击打开同一个工具箱下拉。
- 工具箱不劫持游戏头像点击（头像弹出的原生菜单仍由游戏渲染，MST 只向 `[class*="Header_avatarMenu"]` 菜单顶部注入自己的入口按钮），也不使用旧的 MST 自建头像切换层。
- 工具箱动作顺序固定为：用户名片、技能升级、房屋升级、战斗升级、装备提升、地下城收益、切换角色。
- 工具箱动作列表由 `ToolkitMenuFeature.getActions()` 统一维护，禁止在多个位置复制不同菜单列表。
- 顶部角色名不改变原有布局结构，只做增强：无边框、鼠标指针提示可点击、悬浮标题提示打开当前用户角色名片，支持鼠标点击和键盘打开。
- 工具箱入口（页头按钮、头像弹出菜单入口）、顶部角色名增强和文案刷新必须复用现有 DOM 更新调度，避免重复插入和重复绑定事件。

### 名片

- 用户名片、队伍名片、战斗配装名片和生活配装名片使用同一套卡片结构。
- 头部工具箱按钮直接放进总等级元素（`Header_totalLevel`）内部：总等级 div 加 `mst-header-level-toolkit` 行内 flex class，等级文本与工具箱按钮同一行，不改动原有结构层；总等级保持信息列（`Header_info`）原生位置，其紧后面的兄弟插槽归 MWITools 头部工具宿主（`#mwitools-header-tools`）所有，MST 不得包裹、移动总等级或占用该兄弟插槽——否则双方观察器会各自把元素挪回自己的锚点，打开设置页时页头先变高再还原地抖动。MWITools 宿主自带 `margin: auto` 会在纵向信息列里把自己居中，MST 必须用更高特异性规则把 `margin-left/right` 覆盖为 0、靠信息列的 `align-items: flex-end` 靠右，保持与其单独运行时一致的观感。角色名只做增强：加 `mst-my-character-name-card-btn` class 提供指针样式、悬浮提示（`title`）和点击/键盘打开当前用户角色名片，不加边框、不额外包裹、不改变原有布局结构。不得与 MWITools 的观察器争抢 DOM 所有权。
- 布局由“单双列复选框”和“战斗/生活/全部”三个内容选项组成。
- 队伍名片默认单列战斗布局；普通用户名片默认双列；用户资料入口默认全部布局；战斗配装默认战斗布局；生活配装默认生活布局。
- 战斗布局包含“装备与技能”“战斗等级与房屋”。
- 生活布局包含“装备与技能”“生活工具”“生活等级与房屋”。
- 全部布局按已确认的单双列规则组合四个区块；同一布局下各区块外框尺寸保持稳定。
- 装备、技能、工具和房屋图标使用游戏资源；空技能显示空格，空生活工具显示该位置工具名称。
- 名片数据时间随具体角色变化；生成时间不在卡片底部展示。
- 战力打造分与着装评分的 MWITools 版本对照关系（不得搞混）：MWITools v26 起进行重大重构，v26 之前（含 v25.14）的算法叫“战力打造分”（战斗房屋 + 技能 + 装备强化期望成本，Ratatatata 算法）；v26 起的算法叫“着装评分”（战斗/生活两套分，装备按公平价值与强化计划成本 20% 偏差估值）。MST 名片中：不勾选“启用着装评分”时显示的“战力打造分”对应 MWITools v26 以下版本的战力打造分（参考 `references/legacy-scripts/MWITools/MWITools_v25.14.js`），勾选时显示的“着装评分”对应 MWITools v26 起的着装评分（参考 `MWITools_v26.4.12.js`）。
- 战力打造分（对应 MWITools v25 及以下）提供“启用新版战力分”选项且默认勾选：勾选时按 v26 起着装评分口径计算并分两行展示——战斗分 = 战斗房屋 + 技能 + 战斗装备 + 战斗神龛，生活分 = 生活房屋 + 工具 + 生活装备 + 生活神龛（✦ 标识在文案前，悬浮提示按战斗/生活分别列出各项与神龛分）；物品与房屋按公平价值估值（官方市场价值优先，其次左右报价平均），强化装备按 v26 强化计划成本估值（与公平价值偏差不超过 20% 时仍用公平价值；背部装备与 MWITools v26.4.14 一致：强制保护之镜且允许贤者之镜方案），技能书按等级所需经验折算；公会神龛按角色已解锁公会增益等级的每级代币与信用成本估值（与 MWITools v26.4.14 起一致，生效等级取增益等级与公会神龛等级较小值）；强化装备底子与精炼材料按完整获取成本链估值（市场公平价值、商店购买、制作、精炼四者取最小，递归计价）；公会代币与信用按官方兑换关系由可转换来源物品的市场价折算（`getGuildCreditValue` 同构），不可估值时对应组不计入。不勾选时使用 v25 及以下战力打造分算法（战斗房屋 + 技能 + 装备强化期望成本），单行显示。公共高成本计算只做内存缓存。
- 着装评分与 MWITools 的数值必须保持一致（允许市场行情刷新时机的微小差异），MWITools 更新后必须核对并同步；市场行情数据源固定取当前站点的 `https://${hostname}/game_data/marketplace.json`——在 www、裸域、测试服任一入口页面都读取该站点自己的市场行情（测试服、中文站与正式服的市场相互独立），不得跨服混用。油猴头部 `@match` 必须保持 8 条不删减：`www`/裸域/`test` 三种格式的 `milkywayidle.com` 与 `milkywayidlecn.com` 共 6 条，另加 `milkonomy.pages.dev` 与 `hyhfish.github.io/milkonomy` 2 条；`@connect` 必须覆盖与 `@match` 相同的 6 个游戏站域名（www/裸域/test 各两个站点）。从其他地方（如 MWITools 旧脚本头部）同步此规则时，不得改回按环境分支写死域名的旧写法，也不得删减 `@match` 或 `@connect` 的域名条目。
- 下载和复制名片共用同一图片生成链路，导出效果必须与屏幕显示一致，避免阻塞页面或导致崩溃。

### 房屋升级

- 房屋、升级材料、库存和官方物品等级均从游戏数据读取。
- 顶部起始/目标等级与各房屋列表行相互独立，不得错误联动。
- 未勾选任何房屋时不得计算任何升级材料。
- “添加到购物车”只添加缺失材料，并调用 MWITools 公开购物车接口。

### 技能升级

- 支持技能列表、多技能方案、职业方案、预设目标等级和合计价格。
- 技能搜索支持中文、英文和 hrid；技能名称、图标、经验和等级来自官方数据。
- 未自定义起始等级时，按角色实际等级和经验百分比计算；自定义后按该等级 0% 经验计算。
- 技能图标点击跳转市场；购物车操作只在数量大于 0 且 MWITools 购物车可用时执行。
- 市场技能书交易详情页：点击技能书图标后弹出的悬浮菜单（MuiTooltip 交互弹层，与“打开物品词典”同区域）提供“技能升级计算器”入口，点击后直接打开计算器并预填该技能。
- 技能页（技能 tab，AbilitiesPanel 标题处）的“升级计算器”入口：点击后直接打开计算器并默认填充当前战斗配装（`characterLoadoutMap` 中 `actionTypeHrid === '/action_types/combat'` 的 `abilityMap`，按槽位号排序）已装备的全部技能。
- 技能页技能图标菜单与库存/市场技能书悬浮菜单内的计算器入口按钮：必须与同菜单其他操作按钮视觉一致——统一为游戏主要操作按钮观感（space-600 蓝底、无边框、圆角），不依赖游戏 variant 类是否存在。
- 方案内容以 `references/external-tools/mwi-tool/resources` 为准。
- 技能升级中文市场列头使用“左一 / 总价”和“右一 / 总价”；英文保持 `Best Ask Price / Total` 和 `Best Bid Price / Total`。
- 桌面端技能列表为纵向滚动条预留宽度，默认打开和出现纵向滚动时均不得产生无意义的横向滚动条；窄屏仍允许列表容器自身横向滚动。

### 战斗升级

- 默认显示耐力、智力、攻击、防御，以及近战/远程/魔法中等级最高的职业。
- 耐力、智力固定选修；攻击、防御、近战可选主修或选修；远程、魔法只能主修。
- 所有专业均可选择同修；相邻同修为同一序号，未同修的行开始新序号。
- 一个序号内同一职业只能出现一次；同一职业重复出现时，当前等级和起始等级继承前一行该职业的最大进度。
- 选修经验使用选修经验全额；主修同修使用主修经验；主修非同修使用主修经验加选修经验。
- 列表不包含主修时仍按各行经验速率估算耗时与合计：选修行使用选修经验、设置单独经验的行使用单独经验，不要求列表至少包含一条主修。
- 同修主修的结束等级根据同组持续时间反推，允许产生非 0% 的结束经验，不能手工修改。
- 只有第一列拖动柄可以排序，其他单元格不得触发行拖动。
- 起始和目标等级允许直接输入有效值；目标等级下拉包含 200。
- “使用当前战斗经验”只在用户点击时读取官方 React `GamePage` state 的 `combatStartTime` 与当前玩家 `battlePlayers` 累计经验，并立即填入顶部主修/选修小时经验；该数据不能进入通用角色状态，不能依赖历史采样窗口。
- 当前战斗经验填入规则：只读到 1 个职业时视为主职业总经验并按 3:7 拆为主修/选修；读到 2 个职业时按当前列表职业类型分别填入；读到 5 个职业时汇总后按 3:7 拆分。

### 装备提升

- 使用各职业单刷预设，在统一构造目标下分别模拟基准装备和对比装备，再计算每秒伤害（DPS）差异。
- 计算思路来源于 MWICombatSimulatorTest，战力和每秒伤害（DPS）公共逻辑集中维护。
- 套装按已确认的 +10 方案；技能等级固定为 `4 / 6 / 6 / 6 / 6`。
- 背部为空，护符和饰品（Trinket）不计入每秒伤害（DPS）；项链、耳环、戒指默认对应位置贤者 +5，装备部位选择中不展示护符、饰品（Trinket）和生活工具。
- 双手武器占主手并排除副手；主手和副手可同时存在。
- 基准和对比使用相同随机数序列，降低随机波动。
- 基准装备与对比装备是同一件（同 HRID、同强化等级）时差异必然为 0，直接给出 0 提升且不启动模拟，两栏每秒伤害显示“—”。
- 打开弹窗和切换职业方案后自动开始模拟，不需要用户先手动改动装备。
- 模拟只包含战斗等级与房屋等级这两项角色数据，不计入角色成就和公会神龛等固定增益：这些增益对两件装备的相对比较没有意义，避免它们稀释所选装备的影响。
- 套装价格差只计算两件被比较装备的价格差。
- 结果是统一构造目标下的相对模拟结果，不等同于任意实际怪物上的提升，仅供装备取舍参考。
- 弹窗和属性表按中英文最长内容收紧；桌面端保持表头完整且不横向滚动，窄屏只允许配置区和属性表容器自身横向滚动。
- 详细模拟配置以 `docs/analysis/装备提升模拟基准说明.md` 为准。

### 地下城收益

- 覆盖奇幻、阴森、秘法、海盗四个地下城及 T0-T2。
- 首次打开默认选择按官方 `sortIndex` 排序后的第一个地下城、T0、5 人队伍和 30 分钟单次耗时。
- 界面保留地下城、难度、队伍人数、单次耗时、每日药品/饮料成本、工匠茶、暴饮之囊强化等级和自定义模式；每日药品/饮料成本单位为 `M`，可留空。勾选自定义模式后，额外显示钥匙来源、对应购入方式和货物出售方式。
- 工匠茶默认勾选。暴饮之囊在强化等级前提供与名片双列切换一致的无文本方形复选控件；在当前装备、背包和仓库的全部持有物品中选择最高强化等级，拥有时自动勾选，没有时不勾选。等级选择只由该复选框控制，取消后必须禁用等级选择并移除其饮品浓度加成。
- 操作区控件使用自适应等宽网格，按合理最小宽度自动调整列数；最后一行沿用相同列宽并允许保留空位，不得拉伸少量控件填满整行。桌面端和移动端均不允许重叠或撑出弹窗。
- 提供队伍人数下拉选项 1-5，默认 5；战斗掉落数量（Combat Drop Quantity）固定按 `29.5%` 处理，战斗掉落率（Combat Drop Rate）和统计周期均不提供；每日固定按 24 小时计算。提供“收益扣除市场税”选项且默认勾选：勾选时卖出收入固定扣除 5% 市场税（牛铃袋按 18% 特殊税率）；不勾选时所有物品（含牛铃/牛铃袋）都按市场报价直接计算、不扣任何税。税率数值统一读取 `src/common/constants.js` 的 `MARKET_TAX_RATE` 与 `COWBELL_TAX_RATE`，界面与帮助文案不硬编码百分比，选项悬浮提示说明免市场税范围。
- 每日轮次按 `24 × 60 ÷ 单次通关分钟` 计算，不向下取整，计算链路保留完整精度。
- 普通宝箱每车数量按官方公式 `5 ÷ 队伍人数 × (1 + 29.5%)` 计算；T0 无精炼宝箱，T1 精炼宝箱为每车普通宝箱 × `0.33`，T2 为每车普通宝箱。单车和每日宝箱数量参与计算时保留完整精度，显示时最多保留两位小数。
- 门票数量必须等于普通宝箱期望数量并保留完整精度，不能按实际轮次计算。
- 结果列表必须明确分为上方的材料成本和下方的预期产出；先按输入条件计算普通与精炼宝箱期望数量，再按官方掉落率和数量区间平均值递归展开物品期望数量，不得使用写死的单箱价值。
- 重复掉落项需要合并，嵌套宝箱需要继续递归展开，不可交易代币按官方商店兑换价值折算。市场单侧为 `-1` 时应使用可用回退价格，只有无任何有效价格时才按 `0` 估值并提示。
- 默认模式下，门票和宝箱钥匙必须在同一张表中同时展示制作与购买两套单位和每日成本，不展示每车成本或材料消耗格子；工匠茶与暴饮之囊只影响制作成本。
- 自定义模式允许选择制作钥匙或购买钥匙。制作钥匙时，购入方式作用于门票和开箱钥匙的制作材料；购买钥匙时，购入方式作用于门票和开箱钥匙成品。中文货物出售方式使用“左卖 / 右卖”，购入方式使用“左买 / 右买”；英文继续使用 Ask/Bid 买卖文案。
- 顶部表头只显示“项目 / 数量 / 制作钥匙 / 购买钥匙”分组，不单独保留第二层价格方向表头；“材料成本”分区行只显示左买/右买，“预期产出”分区行只显示右卖/左卖，自定义列同样只显示当前分区相关的价格方向。启用自定义后，左侧两列改为所选钥匙来源的保守与乐观结果，右侧两列合并为一个自定义结果，各行均按自定义购入和卖出参数计算；中文只显示中文价格方向，英文只显示英文价格方向。
- 地下城结果表按中英文内容宽度分配列宽，较长英文项目允许自然换行。默认模式的项目、数量和四个金额列分别为 `27%`、`13%` 和 `15%`；自定义模式使用项目 `27%`、数量 `13%` 和三个 `20%` 的有效金额列，合并后的自定义结果只占一个有效金额列，不得保留双列宽度。表格最小宽度为 `35rem`，弹窗最大宽度为 `38rem`；窄屏只允许结果表容器横向滚动。
- 填写每日药品/饮料成本后，两套每日总成本均增加该固定金额，每日期望收益相应扣除，每车期望收益按每日轮次分摊扣除。

### 战斗模拟器导入

- 目标站点为 aiwwb 战斗模拟器（shykai 模拟器的分支，新增神龛输入）：`https://aiwwb.github.io/milkywayidle_battle/dist/`；模拟器自带“导入/导出”按钮旁注入“单人/组队导入”按钮。

- 按钮位置与 MWITools 一致：插到模拟器“导入/导出”按钮所在 row 之后独占一行，宽度按文案自适应并靠左。
- 模拟器地图下拉不包含的战斗地点（如公会试炼图）匹配失败时保持模拟器当前选择，不强行设置。
- 工具箱菜单在“切换角色”前提供“战斗模拟 aiwwb”入口，图标使用战斗样式；`window.open` 使用固定 target 名（`mst-combat-sim-aiwwb`），重复点击复用同一窗口不新开。

### 配装与利润网同步

- “复制利润网数据”包含 Milkonomy 与 hyhfish 两种数据，结果必须与 EDS 原逻辑一致，包含暴饮等字段。
- 战斗配装页数据必须根据当前正在编辑的配装生成，不得误用身上穿戴。
- 配装名片计算战力时，配装未包含的 10 个工具位从角色当前穿戴补齐。
- 配装名片装备强化等级遵循游戏配装语义：复选框“使用最高强化等级”勾选即 `useExactEnhancement` 为 falsy（与官方 `checked: !useExactEnhancement` 一致），此时从库存与已穿戴中取该物品的最高 `enhancementLevel`（配装 hash 失效时同样按最高强化兜底）；`useExactEnhancement === true`（“使用精确强化等级”）时保持配装 hash 指向的精确等级。
- 名片内容区的装备、技能、房屋图标悬浮提示分两行：第一行物品名称（装备带强化等级 `+N`，技能/房屋带 `Lv.N`），第二行该物品自身的评分数值；评分标签随“启用着装评分”开关切换（勾选为“着装评分”，未勾选为“战力打造分”），单物品评分口径与对应算法的聚合口径一致（装备用单件估值、技能用技能书成本、房屋用房间造价，均折算到 M），无市场价值的物品不显示评分行。
- 名片评分区域可点击，弹出“评分明细”浮层（挂 body 的固定浮层，不新开 Swal——同实例只能一个 popup）：着装评分口径按战斗/生活两组分别列明战斗房屋、技能、战斗装备、战斗神龛与生活房屋、生活工具、生活装备、生活神龛，逐行展示名称（含等级/强化）与分数，各分组标题带该组合计分数；神龛组按每个已激活公会增益一行（官方 guildBuffNames 名称 + 生效等级 `min(个人增益, 公会神龛等级)`，分值为该增益逐级代币与信用成本），与聚合口径同源（`_calculateV26ShrineDetails`）；战力打造分口径为单组，房屋只列有分值的战斗向房间，不计神龛。明细数据与卡片评分同源（`calculateItemScores`），评分模式切换后重算。明细行顺序固定：装备按 主手、副手、头部、身体、腿部、手部、脚部、袋子、背部、项链、戒指、耳环、护符（`SCORE_DETAIL_SLOT_ORDER`，双手武器随主手槽位，官方未列出的饰品槽排护符之后，未知位置排最后）；工具按官方技能顺序（`skillDetailMap` 的 `sortIndex`：挤奶、采集、伐木、奶酪锻造、制作、缝纫、烹饪、冲泡、炼金、强化）排在装备之后；技能按槽位号、神龛按官方神龛 `sortIndex`，房屋保持数据自身顺序；排序只发生在渲染侧（`buildScoreDetailSections`），聚合计算的迭代顺序不得随之改动，避免总分求和顺序漂移。
- 评分明细浮层提供“复制明细”按钮，输出名称与分数同一行的固定格式文本；明细行为 flex 双节点布局，浏览器对手动选取复制按块拆行属复制行为限制，不得为复制而改回单行文本流布局。
- 评分块的悬浮提示保持总分与分项明细（勾选时为战斗着装评分/生活着装评分标题，未勾选时为战力打造分总分）。
- 老利润网指 `milkonomy.pages.dev`；新利润网指 `hyhfish.github.io/milkonomy`，文案不得混淆。

## 六、性能与观察器

- 不因无关高频 WebSocket 消息重渲染 UI；确需处理战斗流水时，只抽取当前功能必需字段写入隔离 runtime，并做节流或按需请求。
- 战斗流水消息必须保持与通用角色数据隔离，避免战斗快照导致名片、配装名片或装备对比显示被战斗中锁定数据污染。
- 所有 `MutationObserver` 必须限定观察范围、过滤自身 DOM 写入并进行去重/调度。
- 禁止观察器回调修改被观察节点后无条件再次触发自身，避免配装页卡死。
- 名片战力计算在测试服全身 +20 场景下目标耗时不超过 0.2 秒。
- 图片生成按角色逐个处理并及时释放临时节点、Canvas、Blob 和对象 URL，避免人数越多页面冻结越久。
- 不在页面加载时初始化当前站点用不到的模块。
