# 订阅通知需求说明书

版本：初版（v1 草案）
状态：待评审
关联文档：`docs/业务功能要求.md`、`docs/工程结构与开发规范.md`

## 一、背景与目标

- 银河奶牛放置是挂机游戏，角色按行动队列（`characterActions`）逐个执行行动。玩家离线或长时间挂机时，需要知道队列何时发生变动（行动完成、队列空了、手动调整等），以便及时回来续队列、补消耗或调整计划。
- 本功能提供"订阅通知"：在游戏内监听特定事件，发生变化时通过 Webhook 推送通知到用户配置的第三方 IM 机器人渠道。
- 初版只支持一种订阅：**行动队列变动通知**；只支持三个渠道：**钉钉机器人、企业微信机器人、飞书自定义机器人**。

## 二、总体说明

### 2.1 运行环境约束（必须遵守）

- 脚本运行在游戏页面内，**只有游戏页面处于打开状态时才能感知队列变动并推送**。浏览器关闭、页面崩溃、断网期间的变化无法感知，通知存在天然缺口，需在 UI 与文档中明确告知用户。
- 推送为跨域请求，必须使用 `GM.xmlHttpRequest`（兼容 `GM_xmlhttpRequest`）发送，禁止使用 `fetch`/`XHR` 直连（CORS 不可控）；相应地 `userscript-header.txt` 必须补齐 `@connect` 域名（见各渠道章节）。
- 站点隔离：本功能只在游戏站（正式服 / 测试服 / 国服）初始化，由订阅总开关统一控制；测试服页面的通知消息必须携带“测试服”标识与角色名，避免正式服与测试服消息混淆。
- 密钥安全：`access_token`、`key`、`secret` 等只保存在本地存储，不得写入任何日志、不得发送到官方 Webhook 以外的地址；密钥类输入框（secret、企微 key）为密码型脱敏，含 token 的 Webhook URL 输入框为明文。

### 2.2 事件源：行动队列（监听消息）

监听官方 WebSocket 消息（已在游戏源码 `main.*.chunk.js` 的 `messageHandlers` 表核对，`v1.20260814.0`）：

| 消息类型              | 官方处理                         | 用途                                                                                                                                                                                                                                                                                        |
| --------------------- | -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `actions_updated`     | `handleMessageActionsUpdated`    | **主要触发源**。增量携带 `endCharacterActions[]`，每条含 `id`、`ordinal`、`actionHrid`、`isDone` 等：`isDone=true` 表示该行动完成并从队列移出；否则按 `id` upsert（新 `id` 即新增、`ordinal` 变化即排序调整）；更新后队列为空且原队列非空即队列腾空（官方自己也是用该消息判空并发空闲通知） |
| `action_completed`    | `handleMessageActionCompleted`   | 单次行动完成，携带 `endCharacterAction` 与 `endCharacterItems`（掉落）、`endCharacterSkills`/`endCharacterAbilities`（经验）。同 `id` 只更新进度；`isDone=true` 时作为完成触发源之一（单步任务可能只发该消息、没有移除增量）                                                                |
| `init_character_data` | `handleMessageInitCharacterData` | 页面加载 / 重连后的完整快照，只用于重建基线快照（不触发推送），携带 `characterActions` 全量；`partyInfo.partySlotMap` 同步本方准备状态作为会话基线                                                                                                                                          |
| `party_updated`       | `handleMessagePartyUpdated`      | 组队准备状态来源：`partyInfo.partySlotMap` 按 `characterID` 匹配本方槽位的 `isReady`，本方从未准备变为已准备时重置组队战斗的进度计数基线与进度计时（不推送通知）                                                                                                                            |

- 变动检测以 **`id` 为准**（`CharacterAction.id`）：模块维护"当前行动 id"。迷宫等多步任务会持续推送 `action_completed` 但 `id` 不变，表示同一任务进行中——`id` 不变一律视为任务内部变动，不推送。只有当前行动 `id` 结束（`isDone=true` 或从队列移除）且队首变为新 `id`，才算一次"任务完成、新任务开始"。
- `CharacterAction` 进度字段：`hasMaxCount`（是否有上限）、`maxCount`（总次数）、`currentCount`（已完成次数）；无限行动 `hasMaxCount=false`。行动名称由 `actionHrid` 查官方 i18n。
- DataHub 现状核对与实现决策：`src/common/data.js` 的 `applyCharacterMessage` 不处理 `actions_updated`/`action_completed`；本功能**由模块单独监听**（`mst:ws:init-character-data` / `mst:ws:message`），未扩展 DataHub。队列排序与官方一致：**partyID 非 0（组队/战斗行动）在前、partyID 为 0（个人生活行动）在后、各组按 ordinal 升序**。取消启发：有限次数任务未达上限被移除（isDone=true）按用户取消处理，**不报完成**，但队首接上的新任务仍按任务开始通知播报（事件类型 `started`，`completedTask` 为空）。
- 通知范围（初版口径，明确收窄）：
  1. **只针对在线时（页面打开期间）的队列变化**；离线期间的变化不感知、不补推（见 2.1 环境约束）。
  2. **队首变化才推送**：当前任务完成、队首换上另一个任务时推送，完成行与开始行同属一条通知（判定与开关见 3.1）。
  3. **任务内部变动不推送**：同 `id` 的 `action_completed`/进度更新（多步任务、战斗波次等）一律不触发。
  4. **长时间未完成走定期进度推送**：当前任务持续超过设定间隔仍未结束时，推送一次进度（见 3.1）。
  5. 队列编辑（新增 / 取消 / 排序调整）本身不触发通知；队列腾空作为完成通知的附加提醒（完成最后一条任务后队列已空时，在该条通知中附加提醒，不单独成条）；队首换成新任务（含取消后接上、空队列入队）由任务开始通知播报。

## 三、订阅定义：行动队列变动通知

### 3.1 触发与内容

- 触发分四类，前两类以队首变化判定：
  1. **完成通知**（事件触发）：当前任务 `id` 以 `isDone` 结束且不算取消时才推送；受"最小推送间隔"限速约束（间隔内多次触发合并为一条，按最新状态发送）；若完成的是队列最后一条（队列已空），同一通知附加腾空提醒。**与任务开始通知同属一条消息**：一次队首变化只发一条，完成行与开始行按各自开关决定是否出现（都关则不推送）。
  2. **任务开始通知**（事件触发，默认开启）：**队首换成另一个任务即推送**，来源包括完成切换、被其他任务顶掉、被挤下去的任务重新回到队首、有限次数任务未达上限被移除的取消切换、队列为空时入队；只按队首变化判定，不区分行动类型——迷宫、个人战斗同样适用，且这些行动自身 `id` 不变也照样推送。同一任务一直在队首连续执行（迷宫跑不同房间/环节、战斗打不同波次）不推送：队首 `id` 未变即无事件。**组队/战斗行动（`partyID` 非 0）例外**：改由开战播报，队首变化时不推送（否则入队一条、开战一条，内容重复）；判定依据是"是否拿到过队伍状态"，拿不到 `partyInfo.party.status` 时退回队首变化播报。**开战播报**：`party_updated` 的 `partyInfo.party.status` 进入 `battling` 时推送一条（此时队首 `id` 未变，队伍先准备就绪、过了等待期才真正开战；官方 `PartyStatus` 为 creating/recruiting/battling/disbanded，官方自己也在该状态进入 `battling` 时发"队伍开战"通知），战斗结束退出 `battling`、下一轮再进入则再推一条，即每次开战各一条。内容为开始行 + 「等待队列」概览（见下）。开启时完成通知不再重复播报新任务；关闭任务开始通知时，新任务由完成通知在一条消息里带出。
  3. **进度通知**（定时触发）：当前任务自开始（或上次进度通知）起超过推送间隔仍未完成时推送；任务完成或 `id` 变化后计时重置。间隔默认 30 分钟（避免长期挂机任务推送大量垃圾消息），允许用户修改（10–240 分钟，可关闭）。
  4. **队列为空提醒**（定时触发）：队列腾空后固定**每分钟**推送一条提醒（与完成/进度通知同构），直到有新任务入队；完成通知中的腾空附加提醒只发一次，周期提醒由此项承担，可在消息类型中单独关闭。
- 消息内容（纯文本，多行，用 `\n` 换行），完成 / 任务开始 / 进度 / 测试通知同构：
  - 第一行标题：`【MST】行动队列`（不含角色名）；
  - 完成通知：`✅ 完成：<行动名>（已完成 X / 共 Y 次）`（无上限任务显示 `（无上限）`）；战斗任务的行动名带官方同款难度后缀 ` (T<tier>)`（`difficultyTier >= 1` 时）；随后列**前 3 个**等待执行的队列内容（行动名（已完成/总次数），不含队首），超出以 `…共 N 项` 收尾；队列已空时以 `⚠️ 行动队列已空，请及时补充` 结尾；开启任务开始通知时不列开始行；
  - 任务开始通知：`▶️ 开始：<行动名>（已完成 X / 共 Y 次）`，随后是与完成/进度通知同口径的 `等待队列：` 概览——不含队首、最多 3 项，超出以 `…共 N 项` 收尾，每项带已完成/总次数；已执行过、轮到时会接着做下去的任务由非零次数直接体现（不限行动类型，无上限行动被顶掉到等待区后同样回到队首接着打），不另列「继续执行」段；
  - 进度通知：`⏳ <行动名>：已完成 <currentCount> 次`（行动名同样带难度后缀），有上限且剩余大于 0 时附 `剩余 <maxCount - currentCount> 次`（没有剩余/无上限则不提示剩余）；同样列出前 3 个**等待执行的**队列内容（不含正在执行的任务）；组队战斗口径：组队/战斗行动（partyID 非 0）在同一条 `CharacterAction` 上持续累加 `currentCount`，取消准备再重新准备不会更换 `id`，因此本方角色重新准备（`party_updated` 中 `isReady` 从未准备变为已准备）视为新的战斗会话——进度通知的已完成次数从重新准备时重新起算（会话内增量），进度计时同步重置；任务切换、基线重建后恢复原始累计口径；
  - 时间行：`yyyy-MM-dd HH:mm:ss` 格式的发送时间；
  - 角色名行：角色名优先；名称不可用但已有角色 id 时显示 `角色 <id>`（区分同站多账号）；两者都没有时显示 `未知角色`（该状态没有基线、定时推送已被拦截，正常只出现在手动测试发送）；测试服页面在上述内容后追加 ` · 测试服` 标识，正式服/国服不追加。
- 行动名称按官方 `getActionDisplayName` 口径组装（游戏源码 `main.chunk.js`）：炼金类（`/action_functions/alchemy`：点金、分解、转化、解精炼）显示「行动名: 物品名」，强化（`/action_functions/enhancing`）只显示「物品名」，两者在物品强化等级 ≥ 1 时追加 ` +<等级>`；其余行动直接用行动名（采集/制作类的 `actionHrid` 本身按物品命名，如 `/actions/cheesesmithing/azure_pot`）。物品取自 `CharacterAction.primaryItemHash`，格式与官方 `computeItemFromHash` 一致（`characterId::itemLocationHrid::itemHrid::enhancementLevel`）；物品解析不到时退回行动名（官方此时显示 `actionsUtil.itemNotAvailable`）。行动名与物品名都走官方 i18n 资源按当前游戏语言显示，取不到时回退 hrid。

### 3.2 订阅配置项

| 配置项           | 类型            | 默认     | 说明                                                                                                                                                                                 |
| ---------------- | --------------- | -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 订阅开关         | 布尔            | 关       | 总开关，关闭时不监听、不推送                                                                                                                                                         |
| 消息类型         | 复选框（多选）  | 全勾     | 行动队列订阅下的通知种类：任务开始通知、任务完成通知、队列为空提醒、定期进度通知（设置弹窗按此顺序排列），允许分别勾选，关闭的种类不推送；开启任务开始通知时完成通知不重复播报新任务 |
| 通知目标渠道     | 单选            | 钉钉     | 初版推送到一个渠道；后续版本可扩展多渠道广播；官方配置说明链接展示在渠道文案后                                                                                                       |
| 最小推送间隔     | 数字（秒）      | 5        | 渠道推送频率下限：两次推送至少间隔该时间，避免触发渠道的推送限流；间隔内的多次触发合并为一条按最新状态发送。范围 5–600                                                               |
| 定期进度推送间隔 | 数字（分钟）    | 30       | 当前任务未完成时的进度推送周期，避免长期挂机任务刷屏；范围 10–240，0 表示关闭                                                                                                        |
| 每分钟推送上限   | 数字（条/分钟） | 渠道默认 | 滑动 60 秒窗口的推送上限，推送时生效；切换渠道自动带出该渠道官方限流默认值（钉钉/企微 20、飞书 100），可改，范围 1–100                                                               |

## 四、渠道需求

### 4.1 钉钉机器人

- 官方文档：https://open.dingtalk.com/document/robots/custom-robot-access
- 官方提供：带 `access_token` 的 Webhook 发送地址，以及（选择加签安全设置时的）加签密钥 `secret`。
- 请求地址：`https://oapi.dingtalk.com/robot/send?access_token=<access_token>`；加签时追加 `&timestamp=<毫秒时间戳>&sign=<签名>`。
  - 注意：官方域名是 `oapi.dingtalk.com`，示例脚本中写的 `dingtalk.com` 不完整，实现以 `oapi.dingtalk.com` 为准；`@connect` 增加 `oapi.dingtalk.com`。
- 加签算法（安全设置选"加签"时必须实现；用户配置了 `secret` 才加签，留空则不加）：
  1. 取毫秒时间戳 `timestamp`；
  2. 待签字符串为 `"{timestamp}\n{secret}"`（中间是真实换行符）；
  3. 以 `secret` 为密钥对待签字符串做 HmacSHA256，得到二进制签名；
  4. Base64 编码，再做 URL Encode，作为 `sign` 参数。
  - 备注核对：用户提供的 shell 示例中 `echo -n "${timestamp}\n${SECRET}"` 在 bash 双引号内 `\n` 是字面反斜杠加 n 而非换行，实际执行需 `printf` 或 `$'...'` 写法；实现以"真实换行符"口径为准，并以官方文档为准回归验证。
- 消息格式（初版仅用纯文本）：

```json
{
  "msgtype": "text",
  "text": {"content": "第一行\n第二行"}
}
```

- 换行使用 `\n`；`content` 最短 1 个字符、最长 500 个字符，超长需截断（末尾加 `…`）。
- 限流：单个机器人每分钟最多 20 条。超出时官方会拒绝并返回错误；客户端按最小推送间隔 + 每分钟推送上限限速，间隔内多次触发合并为最新内容，重试耗尽后丢弃，不硬刚限流。
- 官方安全设置说明：钉钉机器人必须至少启用一种安全设置（自定义关键词 / 加签 / IP 白名单）。自定义关键词与"【MST】"前缀天然兼容；加签由本功能按上述算法支持；IP 白名单不适用于家庭宽带场景，文档中提示用户不要选。
- 返回判断：HTTP 200 且 JSON `errcode == 0` 为成功；`errcode != 0`（如 310000 签名错误、130000 限流）记为失败，进入重试/降级。
- 错误处理：失败按指数退避重试（1/2/4 分钟，最多 3 次）；最终失败在游戏内设置页显示最近一次失败原因（时间 + errcode/errmsg）。

### 4.2 企业微信机器人

- 官方文档：https://developer.work.weixin.qq.com/document/path/99110
- 官方提供：Webhook 发送地址中的 `key`。
- 请求地址：`https://qyapi.weixin.qq.com/cgi-bin/webhook/send?key=<key>`；无独立签名环节，`@connect` 增加 `qyapi.weixin.qq.com`。
- 消息格式（初版仅用纯文本）：

```json
{
  "msgtype": "text",
  "text": {"content": "第一行\n第二行"}
}
```

- 换行使用 `\n`；官方限制单条请求体不超过 4096 字节，`text.content` 按官方文档不超过 2048 字节（实现按 2048 字节做保守截断，注意 UTF-8 多字节字符按字节截断且不得截断出残缺字符）。
- 限流：约每分钟 20 条（每个机器人）。超出返回限流错误；客户端策略与钉钉一致（最小推送间隔 + 每分钟上限限速，间隔内合并为最新内容，重试耗尽后丢弃）。
- 返回判断：HTTP 200 且 JSON `errcode == 0` 为成功；常见失败 `errcode 93000`（webhook 无效/被移除）等，处理同 4.1。
- 其他说明：企业微信机器人无需加签，配置项只有 `key` 一项；群机器人无需可信 IP，但 webhook 与群绑定，群解散后失效，需在设置页给出"最近失败原因"帮助用户定位。

### 4.3 飞书自定义机器人

- 官方文档：https://open.feishu.cn/document/client-docs/bot-v3/add-custom-bot
- 官方提供：Webhook 请求地址（形如 `https://open.feishu.cn/open-apis/bot/v2/hook/<hook-id>`），以及（启用签名校验时的）签名密钥 `secret`。允许用户直接粘贴完整 Hook 地址或只填 hook-id（二选一，界面上做成单输入框自动识别）。
- 请求地址：用户配置的 Hook 地址；`@connect` 增加 `open.feishu.cn`（若允许自定义企业域名，额外对任意 `https://*` 的 Hook 地址提示需自行确认，初版只内置 `open.feishu.cn`）。
- 签名（仅当用户在飞书后台启用"签名校验"时需要；配置了 `secret` 才签）：
  1. 取**秒级**时间戳 `timestamp`（与钉钉的毫秒不同）；
  2. 待签字符串为 `"{timestamp}\n{secret}"`（真实换行符）；
  3. **以待签字符串为 HMAC 密钥（消息体为空）**做 HmacSHA256 后 Base64 编码（与钉钉的 key=secret 相反）；
  4. 不做 URL Encode，放进请求头：
     - `X-Lark-Request-Timestamp: <timestamp>`
     - `X-Lark-Request-Sign: <sign>`
- 消息格式（初版仅用纯文本）：

```json
{
  "msg_type": "text",
  "content": {"text": "第一行\n第二行"}
}
```

- 请求体（含签名头无关，指 body）大小不能超过 20 KB；本功能消息体远小于该值，超长保护按 4.1 截断策略执行即可。
- 限流：单租户单机器人 100 次/分钟、5 次/秒。客户端除每分钟合并外，另需保证相邻两条请求间隔 ≥ 1 秒（5 次/秒的秒级限制在本场景不易触发，但队列补发时必须限速）。
- 返回判断：HTTP 200 且 JSON `code == 0` 为成功（飞书是 `code`/`msg` 字段，与钉钉/企微的 `errcode` 不同）；签名错误返回非 0 `code`，处理同 4.1。
- 其他说明：飞书签名要求请求体与签名所用时间戳一致即可，无消息级额外限制；自定义机器人安全设置中"自定义关键词"同样与"【MST】"前缀兼容。

## 五、非功能需求

### 5.1 可靠性与限流

- 发送队列：所有渠道共用一条内存发送队列 + 本地限速器（最小推送间隔 + 每分钟推送上限滑动窗口）；页面关闭队列即丢弃（不做跨会话补发，初版不承诺离线补推）。
- 重试：网络错误或非成功响应按 1/2/4 分钟退避重试，最多 3 次，重试耗尽后丢弃；重试期间新的完成事件仍会按最新状态生成通知，不做逐条排队重放。
- 幂等：以当前行动 `id` + 完成事件去重，同一任务完成只发一条；进度通知按周期计时，天然不重复。

### 5.2 性能

- 变动检测在消息驱动时同步执行（`id` 比对 + 计数更新），开销可忽略；进度通知允许使用一次性定时器，不得引入高频常驻轮询。
- 推送失败不得阻塞或抛出到游戏页面控制台之外；错误收敛为 `console.warn` 与设置页状态展示。

### 5.3 安全与隐私

- 凭据仅存本地（localStorage 或 GM 存储，与现有存储规范一致）；secret 与企微 key 输入框为密码型脱敏；含 token 的 Webhook URL 输入框为明文（钉钉地址、飞书地址）。
- 日志中不得输出完整 webhook 地址与密钥；调试输出只保留域名与 `errcode/code`。
- 推送内容仅包含游戏行动队列信息，不含角色资产等其他数据。

### 5.4 配置 UI 与存储

- 入口：工具箱下拉菜单新增"订阅通知"入口（位于用户名片下方），打开设置弹窗；弹窗分通用配置与渠道配置两区，含订阅配置（3.2）、渠道凭据（url/key/secret）、每分钟推送上限与测试发送按钮。
- "测试发送"按钮：立即向当前配置渠道发送一条固定测试文案，回显成功/失败与官方错误码，用于开通后自检。
- 存储边界（明确收窄）：
  - **只有配置持久化到本地，且按角色分用户存储**：订阅配置（3.2）与渠道凭据（url/key/secret）按现有 `MST_*` 前缀约定存 localStorage/GM 存储，新增键在 `data.js` 的 `STORAGE_KEYS` 登记，配置读写走统一存储工具；同一存储键下以 `characterId` 分桶，不同角色的渠道凭据与开关互不影响（旧版单角色扁平结构自动迁移到当前角色名下）。
  - **其余一律只存内存**：当前行动 `id` 基线、防抖/进度计时器、发送队列、"最近失败原因"等运行时状态不落盘；页面刷新或关闭即丢弃，下次由 `init_character_data` 重建基线。
  - **不保存过期与不必要的信息**：不持久化队列快照、变动历史、已发通知记录；切角色或任务切换后旧任务的内存状态立即释放（重置 `id` 基线并清掉计时器），不保留跨任务、跨会话的残留。
- i18n：全部界面文案进入 `src/common/messages.js`，中英文完整。

## 七、验收标准（初版）

1. 开启订阅并配置钉钉/企微/飞书任一渠道后，当前任务完成、新任务开始时收到一条纯文本完成通知，内容符合 3.1（完成行动名 + 新任务 + 前 3 个队列内容）且语言随游戏语言。
2. 同一任务（如迷宫）期间收到多次 `action_completed`，只要 `id` 不变就收不到完成通知；到达设定的进度间隔后收到一次进度通知（含已完成次数，有上限且剩余 >0 时含剩余次数）。
3. 队列最后一条任务完成时，完成通知中包含"队列已空"提醒；编辑队列（加/删/排序）不产生任何通知。
4. 刷新页面或断线重连后，当前任务未变化时不重复推送。
5. 三渠道"测试发送"均能成功收到测试消息；故意填错 `secret` 时设置页能展示对应官方错误（钉钉 310000 / 飞书签名 code 非 0）。
6. `yarn run check` 通过；新增 `id` 判定（同 `id` 不推送、`id` 变更触发完成通知）、进度周期计时（`hasMaxCount`/剩余次数口径）、签名生成（钉钉 URL Encode 与飞书秒级时间戳差异）、超长截断、发送队列限速的单元测试。
7. Playwright MCP 实际页面验证：真实完成一个任务（队列队首 `id` 变化）确认收到完成通知，多步任务期间同 `id` 的 `action_completed` 不触发推送，控制台无 MST 业务错误；`@connect` 域名齐备、无 CSP/CORS 报错。
8. 头部 `@connect` 新增 `oapi.dingtalk.com`、`qyapi.weixin.qq.com`、`open.feishu.cn`，且不删减既有条目。

## 附：渠道官方能力清单（从官方文档/资料核对）

### 钉钉自定义机器人

- 可从官方获取：Webhook 地址（含 `access_token`）、加签 `secret`（安全设置选择"加签"时由钉钉生成）、安全设置三选一（自定义关键词 / 加签 / IP 白名单）。
- 支持消息类型：text、link、markdown、actionCard、feedCard（初版只用 text）。
- 限制：每个机器人 20 条/分钟；text 内容 1–500 字符；必须至少配置一种安全设置。
- 备注：加签 `sign` 需 URL Encode；时间戳为毫秒且与请求间隔不能超过 1 小时。

### 企业微信群机器人

- 可从官方获取：Webhook 地址（含 `key`），群内添加机器人即得。
- 支持消息类型：text、markdown、image、news、file、template_card 等（初版只用 text）。
- 限制：约 20 条/分钟；请求体上限 4096 字节；text 的 content 官方限制 2048 字节。
- 备注：无签名机制，凭据泄露即可被任意调用，泄露后需在群内重置机器人。

### 飞书自定义机器人

- 可从官方获取：Webhook Hook 地址（含 hook token）、签名校验 `secret`（安全设置选择"签名校验"时生成）；安全设置可多选（自定义关键词 / 签名校验 / IP 白名单，白名单不适用本场景）。
- 支持消息类型：text、post、share_chat、image、interactive 卡片等（初版只用 text）。
- 限制：单租户单机器人 100 次/分钟、5 次/秒；请求体不超过 20 KB；时间戳为秒级且与服务器时差超过 1 小时签名失效。
- 备注：签名放在请求头而非 URL；`code == 0` 才算成功。
