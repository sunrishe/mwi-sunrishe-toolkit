# 战力分算法对照与性能优化

本文记录 MST 名片战力分与 MWITools 两个版本的对照关系、MWITools v25 的卡顿问题根源，以及 MST 历史代码已做并必须保留的性能优化，防止后续改动把优化弄丢或把算法改回卡顿版本。

## 一、MWITools 版本对照关系（勿混淆）

- **MWITools v26 之前**（含 `references/legacy-scripts/MWITools/MWITools_v25.14.js`）：算法名"战力打造分"（Ratatatata 算法）——战斗房屋（7 个房间）+ 技能（50/500 经验折算）+ 装备（强化等级 >1 按强化期望成本、否则市场价 0.5/0.5 加权）。
- **MWITools v26 起**（`references/legacy-scripts/MWITools/MWITools_v26.4.12.js`）：重构为"着装评分"——战斗/生活两套分，装备按公平价值与 v26 强化计划成本（20% 偏差）估值。**v26.4.14 起**（`MWITools-v26.4.14.js`）新增公会神龛分：按角色已解锁公会增益等级累加每级代币与信用成本（战斗/生活分组，`getGuildShrineValues`），任一组不可估值时为 null 不计入。游戏规则补充（`renderGuildBuffModal` 的 `Math.min(o, r)`）：生效等级取角色增益等级与公会神龛等级（`guildBuildingLevelMap` 中对应神龛建筑）的较小值。v26.4.14 的背部装备策略为"强制保护之镜但允许贤者之镜方案"（`getEnhancedEquipmentCost` 恒传 `allowPhilosopherMirror: true`）。
- **MST 名片**：不勾选"启用着装评分"→"战力打造分"对应 v25 及以下；勾选 →"着装评分"对应 v26 起（含 v26.4.14 的公会神龛分）。自 2.10.1 起全面对齐 v26.4.14：强化装备底子与精炼材料按完整获取成本链估值（`acquisitionCostValue` 同构：市场公平价值、商店购买、制作、精炼取最小，递归计价并带循环检测与结果缓存；精炼与 charm 配方按配方原样，不含依赖玩家实时状态的茶消耗投影）；公会代币与信用按官方兑换关系由可转换来源物品的市场价折算（`getGuildCreditValue`/`getGuildTokenValue` 同构），不再因无直接市场价而漏算；背部装备允许贤者之镜方案。市场行情数据源按当前站点环境分支（测试服/中文站/正式服），与 `getMarketApiUrl` 一致。
- MST 源码结构：`src/modules/character-card/build-score/legacy.js`（v25 战力打造分）、`v26.js`（v26 着装评分）、`index.js`（服务入口组装）。

## 二、MWITools v25 卡顿问题根源

v25.14 的强化期望成本计算存在明显性能问题（每件强化装备都要做大量重复计算），根源如下：

1. **成本重复计算**：`findBestEnhanceStrat`（v25 约 5390 行）在 `protect_at` 循环（2..目标等级）内**每次**调用 `getCosts(itemHrid, price_data)`。`getCosts` 内部会调用 `getRealisticBaseItemPrice` → `getBaseItemProductionCost` → `getActionHridFromItemName`，后者遍历整个 `actionDetailMap` 全表查找配方，并对 `inputItems` 做 `JSON.parse(JSON.stringify(...))` 深拷贝。每件装备约 20 次循环 × 全表遍历 + 深拷贝。
2. **强化期望无缓存**：`Enhancelate`（v25 约 5421 行）使用 mathjs 创建 20×20 对象矩阵并求逆（`math.zeros` / `math.inv`），每次 `protect_at` 都重建矩阵重新求逆，且没有任何结果缓存；`findBestEnhanceStratWithPhiMirror` 的 `lowerBest` 循环（约 9..目标等级）还会把上述过程再重复一遍。
3. **无服务级缓存**：整页多次计算、多个角色名片都不复用结果。

## 三、MST 历史优化（必须保留，对应 legacy.js 位置）

MST 从 EDS/MST 历史（`references/legacy-scripts/mst/mst.script.user.2.4.0-20260730.js`、`2.5.0-baseline.js`）继承并保留了以下优化，本次与 v25 对齐时已逐项核对仍在：

| 优化点           | v25 原状                                 | MST legacy.js 现状                                                                                                                                                                                                            |
| ---------------- | ---------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 强化成本只算一次 | `protect_at` 循环内每次调 `getCosts`     | `_findBestEnhanceStrategy(itemHrid, level, clientData, costs)` 的 `costs` 参数在循环外计算、循环内复用（legacy.js:178-179）；`_findBestEnhanceStrategyWithPhiMirror` 的 `itemCosts`/`baseItemCosts` 各算一次（legacy.js:139） |
| 强化期望缓存     | mathjs 矩阵每次重建、无缓存              | `enhancementExpectationCache` 按 `[强化等级, protectAt, totalBonus, 祝福茶]` 缓存期望结果（legacy.js:207,231）                                                                                                                |
| 矩阵求逆实现     | mathjs 对象矩阵（内存分配大）            | 自研 `_invertMatrix`，`Float64Array` 连续数值数组、原地高斯消元（legacy.js:240 附近，注释保留 Gauss-Jordan 运算顺序）                                                                                                         |
| 物品名→配方查找  | 每次遍历整个 `actionDetailMap`           | 优先查 `DataHub.clientData.indexes.actionNameToHrid` Map 索引（O(1)），索引缺失才回退遍历（legacy.js:130-132）                                                                                                                |
| 配方材料深拷贝   | `JSON.parse(JSON.stringify(inputItems))` | 直接遍历 `inputItems`，不深拷贝                                                                                                                                                                                               |
| 服务级缓存       | 无                                       | `scoreCache`（WeakMap 按角色数据缓存整次结果）、`marketPromise`（市场数据只加载一次）                                                                                                                                         |

## 四、防回归注意事项

- 战力打造分（legacy.js）的强化成本计算是性能敏感区：新增循环、去掉 `costs` 参数复用、去掉 `enhancementExpectationCache`、改回全表遍历或深拷贝，都会退回 v25 的卡顿。
- 与 v25 数值对齐的前提是保留上述优化；测试 `tests/build-score.test.js` 覆盖了 legacy 数值（+12 靴子按强化成本、+0 靴子按市场价加权）和着装评分 v26 断言，改动后必须跑 `yarn run check`。
- 全身 +20 场景着装评分约 139ms、战力打造分约 76ms（Node 测试环境），要求不超过 0.2 秒（`docs/业务功能要求.md`）。引入完整获取成本链（`_v26AcquisitionCostValue` 递归 shop/craft/refine）后首算从约 113ms 升到约 139ms，仍在要求内；递归结果按单次评分上下文缓存（`context.cache`），动作产出/商店奖励/信用来源索引按客户端数据实例级缓存，不得改成每次遍历全表。
- 与 MWITools 的已知微小差异（可接受）：市场公平价值读取时机（MST 用实时数据、MWITools 首次估值时冻结快照）；精炼与 charm 配方的茶消耗投影缺失（依赖玩家实时茶槽/效率/速度状态，MST 按配方原样计价）；v25 legacy 与 MWITools v25 的其余降级项保持原样。官方市场价值（`marketItemValues`）读取：游戏启动早期官方接口可能抛错，MST 降级读 localStorage 原始缓存兜底（`market.js loadMarketItemValues`），保证与 MWITools 的指导价口径一致。MWITools 更新后必须重新核对本清单。
