## 一、背景与目标

- 市场是游戏金币收支的主要渠道，但官方只在「我的挂牌」保留当前还能看到的内容：有效挂牌、以及成交后尚未领取的物品/金币；**领取之后官方就把该挂牌从数据里删除**（官方 `updateMyMarketListings`：仅保留 Active 或未领取数量 > 0 的条目），玩家无法回看自己的历史成交。
- 本功能在本地长期留存玩家自己的市场交易记录：挂牌创建、部分成交、成交完成、取消、过期、领取，以及「立即购买 / 立即出售」（直购/直售）订单，并提供可搜索、可排序、可统计、可导入导出的列表页面。
- 数据范围：**只记录当前用户自己的交易**；不追踪他人交易，不修改游戏行为，不自动下单，不上传任何服务器。

## 二、术语与口径

| 术语           | 含义                                                                                                                                                                                                                        |
| -------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 挂牌 / 订单    | 官方 `market_listings_updated` 中的 MarketListing，即「发布出售挂牌 / 发布购买订单」产生的单据，以官方 id 标识                                                                                                              |
| 直购 / 直售    | 官方「立即购买 / 立即出售」，请求为 `post_market_order` 且 `isInstantOrder=true`                                                                                                                                            |
| 领取           | 官方 UI 的「收集」：把已成交挂牌的未领取物品/金币收回；领取请求带 `marketListingId`                                                                                                                                         |
| 实际到账       | 已成交单据实际到手的金额/物品，取自官方返回的未领取数量（`unclaimedCoinCount` 为扣税后金币、`unclaimedItemCount` 为物品数）；实时链路**不按税率估算**，只有完全没有官方线索的归档记录才按 §4.6 推算（出售扣税、购买不扣税） |
| 环境           | 游戏服务器环境，只有两个：**正式服**（`milkywayidle.com` 与 `milkywayidlecn.com`，cn 为官方中国镜像入口）与**测试服**（`test.*`）                                                                                           |
| 部分成交后取消 | 挂牌先成交了一部分（`filledQuantity > 0`），剩余部分被取消/过期，官方对象同时带成交进度与终态                                                                                                                               |
| 记录时间       | 官方数据不含任何时间戳，本功能所有时间均为插件观测到该变化的本机时间（见 §4.4）                                                                                                                                             |

官方状态取值（`MarketListingStatuses`）：`/market_listing_status/active`、`/filled`、`/cancelled`、`/expired`。

## 三、运行环境与总体约束

- 只在游戏站（正式服 / 测试服）初始化；其余站点不注册消息监听、不写存储、不注入入口。脚本 `@run-at document-start`，WebSocket 数据桥在游戏建立连接前安装，登录快照不会漏收。
- **离线不做实时记录**（页面关闭期间没有数据源）。离线期间完成的订单在下次登录时以「已成交 + 未领取」出现在官方全量快照里，按订单 id 合并补记；用户手动收集时再按订单 id 合并领取信息（见 §4.3）。
- 数据存储使用油猴存储（`GmApi.getValue` / `GmApi.setValue`，兼容 `GM_getValue` / `GM_setValue`），**不使用 localStorage**；GM 存储在油猴管理器内按脚本保存，不随站点清理，且可跨标签页共享（用 `GM_addValueChangeListener` 同步）。
- **数据完全按用户隔离**：记录只保存在本机油猴存储，按「环境 + 角色」分桶；导入导出只处理本人数据，不涉及任何服务器上传或分享；正式服与测试服分开，cn 与 .com 同属正式服（同一角色在两端登录时 id 相同，记录直接归入同一桶）。
- 沿用现有公共能力，不新增运行时依赖：`mst:ws:message` / `mst:ws:send` / `mst:ws:init-character-data` 事件（`src/common/data.js` 的 WebSocket 桥）、`DomObserverService` + `GameUiAdapter`、`Notifier` / `TemplateRenderer`、`i18n`、`SpriteService`、`LanguageEvents`。
- 同页多实例防重：单例标记写在页面 window（`ctx.pageWindow`），规则与市场加购、迷宫补充补给一致。

## 四、事件源分析（官方源码核对）

### 4.1 官方消息与请求总表

| 方向 | 消息 / 请求                                          | 官方处理                                                                                   | 对本功能的用途                                                                                                                                   |
| ---- | ---------------------------------------------------- | ------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| 入   | `init_character_data.myMarketListings`               | `handleMessageInitCharacterData` → `initializeMyMarketListings`                            | 登录/重连全量快照：补齐有效挂牌、未领取的已成交挂牌（含离线期间完成的订单），并做对账                                                            |
| 入   | `market_listings_updated.endMarketListings`          | `handleMessageMarketListingsUpdated`                                                       | **主要数据源**：新挂牌、增量成交、状态变化（Filled/Cancelled/Expired）、领取后清除                                                               |
| 出   | `post_market_order`                                  | `sendPostMarketOrder(isSell, itemHrid, enhancementLevel, quantity, price, isInstantOrder)` | **挂牌出售 / 挂牌购买 / 直购 / 直售的唯一来源**（`isInstantOrder` 区分）；挂牌类请求用于预登记（见 §4.5）                                        |
| 出   | `cancel_market_listing`                              | `sendCancelMarketListing(marketListingId)`                                                 | 记录「取消请求时间」，状态以随后的 WS 消息为准                                                                                                   |
| 出   | `claim_market_listing` / `claim_all_market_listings` | 领取单个 / 全部（携带 `marketListingId`）                                                  | 领取挂单收益 / 挂单物品的**唯一请求**：只记领取请求时间；金额在成交完成时已计入（v2.20.0 起，见 §4.6）                                           |
| 出   | `get_my_market_listings`                             | `sendGetMyMarketListings()`（无载荷）                                                      | 预留请求：当前客户端版本（v1.20260927.0）只有定义与 props 传递、**没有实际调用点**；将来启用时响应同样是 `market_listings_updated`，会被正常处理 |
| 入   | `market_item_order_books_updated`                    | `handleMessageMarketItemOrderBooksUpdated`                                                 | 不用于记录（仅订单簿展示，官方快照数据，无个人单据信息）                                                                                         |
| 入   | `market_item_values_updated`                         | `handleMessageMarketItemValuesUpdated`                                                     | 不用于记录（只更新官方市场价值）                                                                                                                 |

说明：官方全部消息类型（v1.20260927.0 的 `messageHandlers` 表）中与市场相关的只有上表三类；**没有专门的「订单创建/成交回执/领取完成」消息**，挂牌的一切变化都通过 `market_listings_updated` 表达。客户端对 `myMarketListingMap` 的写入只有两处——登录快照 `initializeMyMarketListings` 与 `handleMessageMarketListingsUpdated`（按官方 `updateMyMarketListings` 的规则：`Active` 或未领取数 > 0 则保留，否则删除该条目），**没有本地乐观更新**，因此领取后条目从「我的挂牌」消失必然依赖服务端推送带「未领取归零」的 `market_listings_updated`；v2.20.0 的请求补记在此之外额外兜底（捕获窗口、推送延迟或缺失时也能记录）。

### 4.2 挂牌对象字段（客户端实际读取的字段）

| 字段                  | 类型    | 说明                                                                                  |
| --------------------- | ------- | ------------------------------------------------------------------------------------- |
| `id`                  | number  | 服务器分配的挂牌 id，快照内唯一（官方 `initializeMyMarketListings` 按 id 排序建 Map） |
| `itemHrid`            | string  | 物品 hrid，如 `/items/abyssal_essence`                                                |
| `enhancementLevel`    | number  | 强化等级 0–20                                                                         |
| `isSell`              | boolean | true = 出售挂牌，false = 购买挂牌                                                     |
| `orderQuantity`       | number  | 挂牌总数量                                                                            |
| `filledQuantity`      | number  | 已成交数量（≤ orderQuantity）                                                         |
| `price`               | number  | 挂牌单价（金币，整数）                                                                |
| `workingPrice`        | number  | 受可交易区间限制时的实际生效价格（官方 `getBookPrice` 优先取它）                      |
| `status`              | string  | `active` / `filled` / `cancelled` / `expired`                                         |
| `unclaimedItemCount`  | number  | 官方未领取物品数（购买挂牌成交后未收取的物品）：只作增量对账基准，不展示              |
| `unclaimedCoinCount`  | number  | 官方未领取金币数（出售挂牌成交后未收取的金币，已扣税）：同上                          |
| `characterID`         | number  | 挂牌归属角色 id（客户端界面不读，实测服务端会下发）                                   |
| `createdTimestamp`    | string  | **官方创建时间**（ISO 字符串、纳秒精度，`Date.parse` 截断到毫秒）                     |
| `expirationTimestamp` | string  | **官方过期时间**（创建时间 + 30 天）                                                  |
| `taxTaken`            | number  | 本单累计税费（随成交累加）                                                            |
| `coinsAvailable`      | number  | 购买挂牌当前预留金币（MST 不记录，仅说明字段存在）                                    |
| 其他                  | —       | 官方对象**没有成交时间、没有对手方信息**                                              |

### 4.3 状态变化与观测点（全部以订单 id 为主线）

1. **创建**：可观测到「本地没有该 id、消息/快照里出现新 id」。此时记录创建时间 = 观测时间。
2. **部分成交**：`status` 仍为 Active，`filledQuantity` 增大；两次观测之间的差值即这一段的成交量，`unclaimed*` 的增加量在本轮就计入收入/支出（§4.6）。记录首次成交时间与累计进度。
3. **成交完成**：`status` 变为 Filled，同时 `unclaimedCoinCount`（出售）或 `unclaimedItemCount`（购买）> 0。记录完成时间；**订单在这一刻就算完成**，未领取部分同时计入收入/支出（§4.6），不依赖玩家是否领取。
4. **部分成交后取消 / 过期**：`status` 变为 Cancelled / Expired，`filledQuantity` 保留已成交部分，未成交部分退回。记录取消/过期时间；**统计只计已成交部分**（见 §5.6）。
5. **登录快照补齐**（页面关闭期间创建/成交的订单，或脚本没收到创建消息、只在下一次登录快照里出现的订单）：下次登录的全量快照 `init_character_data.myMarketListings` 必然带着这些订单——**一个都没成交**的（`status=active`、`filledQuantity=0`）、**部分成交**的、以及**全部成交待领取**的（`status=filled` 且未领取数 > 0）。补齐时按订单 id 新建或合并记录：物品 / 数量 / 单价 / 官方创建与过期时间 / 税费 / 已成交数量 / 可领取金额一次取齐（金额按 §4.6 的成交即入账口径立即计入）；有官方 `createdTimestamp` 的创建时间直接用官方值、不标推断，没有时才标推断，成交/完成时间取快照观测时间。新建记录的**环境与角色取当前会话**（测试服记录不写进正式服桶），已有记录保持首次记录时的归属。
6. **领取**：收到携带 `marketListingId` 的 `claim_market_listing` / `claim_all_market_listings` 请求记「领取请求时间」；观测到同 id 条目的未领取数归零（或条目从快照消失）时补一条**领取确认**（时间 + 本次取走的金额明细）。**金额不在这里产生**——订单在成交完成（观测到未领取值增加）时就已经计入收入/支出（§4.6），领取只是把钱取到手；服务端会推送归零条目（§4.1），但领取请求与推送都可能在脚本就绪窗口内丢失，因此领取确认是参考信息、不影响金额。领取后官方删除该条目，本地记录保留。
7. **兜底：未观测结束**（仅出现在「离线期间被取消/过期」这种既没有未领取、也无法在快照里找到的情况）：本地为 Active 的记录在下一次全量快照中不存在且没有观测到终态，标记「已结束（原因未观测）」，可被其他设备导出的终态覆盖。该标记是**快照推断**：之后只要再观测到该 id 的条目（哪怕仍是 Active）就立即解除。
   - 快照对账只在官方确实下发 `myMarketListings`（数组，可为空）时进行：字段缺失时**不做任何推断**，避免把「没有快照」当成「所有条目都不在了」而误标已领取 / 未观测结束（v2.20.0 起 `reconcileWithSnapshot` 对非数组入参直接返回空结果；装配层不再把缺失字段退化成空数组，否则等于「我的挂单一条不剩」）。
   - **只看快照取数时间之前观测到的记录**：快照时间取官方 `currentTimestamp`（脚本晚于登录事件初始化、用 DataHub 兜底补对账时，处理时刻晚于快照本身）。`updatedAt` 晚于快照时间的记录不在快照里只是因为快照没赶上（队列里排在它后面的消息还没处理），按「条目已不在」收尾会把还在进行的订单误标结束、把刚落账的钱误记成已领取（v2.20.0 起 `reconcileWithSnapshot` 支持 `snapshotAt` 并按它过滤）。

### 4.4 已知限制

- **时间口径**：创建时间与过期时间取官方 `createdTimestamp` / `expirationTimestamp`（实测 2026-10-02 确认服务端会下发），不再标「推断」；**成交/取消/领取时间官方不提供**，仍是观测时间（离线完成的订单只能用「快照首次出现/消失」近似）。
- **无实际成交价**：直购/直售请求里是「委托价 + 数量」，实际可能按更优的挂牌价成交（官方规则：买单按最高价预留金币，低价成交退差额；卖单同理），插件无法从消息中还原精确成交明细。
- **无对手方信息**：官方不下发对手方，记录中不包含交易对象。
- **领取后消失**：这是本功能存在的根本原因，也意味着必须自行落库；否则领取一次就丢一条。
- **多设备 / 多标签页**：GM 存储按浏览器配置保存，两个设备各自记录一部分（设备 A 挂单、设备 B 看到成交），需要靠导出/导入合并（§7.8）。

### 4.5 直购/直售的记录策略

**优先按订单 id 与挂牌同构记录**（评审确认口径）：

1. 直购/直售如果由服务端产生带 id 的订单条目，则生命周期与挂牌完全一致——创建、部分/全部成交、取消/过期、领取，全部按订单 id 记录，仅以类型区分「立即购买 / 立即出售」（记录 `kind='instant'` 与 `isInstantOrder` 标记）。
2. 支持「直购也产生带 id 条目」的官方证据：① 官方游戏指南概览写「直接与现有挂牌立即成交」与「创建挂牌」两种方式后，紧接着说「请在『我的挂牌』中领取买到的物品和出售所得」；② 领取请求 `claim_market_listing` 的载荷是 `marketListingId`——领取的对象始终是一条带 id 的挂牌条目；③ 官方 `updateMyMarketListings` 对「已成交但有未领取」的条目会保留在「我的挂牌」里，正好承接直购的待领取物品/金币。
3. 静态源码只能确认出站请求里没有订单号（`postMarketOrderData` 只含 `isSell/itemHrid/enhancementLevel/quantity/price/isInstantOrder`），id 由服务端在条目里下发，需要实测：**开发第一步在真实页面用最小金额的直购/直售实测**，确认 `market_listings_updated` 是否在请求后推送对应条目。
4. 若实测没有服务端条目，走兜底路径：以出站请求为准立一条记录（物品、等级、数量、委托价、发起时间、完成时间 = 发起时间），10 秒内若出现内容匹配的新条目（同 itemHrid、同强化等级、同 `isSell`、同 `price`、同 `orderQuantity`）则关联补全官方 id 与进度，否则保留请求记录并标注「委托价，实际成交价可能更优（差额退还）」，本地生成 id 供跨设备内容去重（§5.5）。
5. 无论哪条路径，领取时都以订单 id 合并（§4.3 第 6 条）。

**实测结论（2026-10-02，正式服 `www.milkywayidle.com`，角色 dadada6）**：用 1 个糖、限价 10 做「立即购买」，请求后官方既没有推送新的挂牌条目，游戏自己的「我的挂牌」Map 也没有新增条目（成交直接结算、物品直接进背包）；对照的出售挂牌请求则立即出现带 id 的新条目。因此**直购/直售走兜底路径**：以出站请求为准落记录（`kind='instant'`、无官方 id），界面标注「未收到官方条目，按委托信息记录（实际成交价可能更优，差额会退还）」；后续若游戏改为下发条目，`linkInstantRecords` 会自动按内容关联，代码无需改动。同轮实测还确认出售挂牌的完整链路（创建 → 成交 → 可领取 → 领取确认；v2.20.0 起金额在成交完成时计入）与取消链路，见 §11.2 验证记录。

### 4.6 收入 / 支出金额的来源（成交即入账，不按税率估算）

- 官方没有独立的「结算/到账」消息，**但金额就在挂牌对象里**：出售挂牌每次成交后，官方把**扣税后的金币**累计进 `unclaimedCoinCount`（未领取金币）；购买挂牌成交后把**物品**累计进 `unclaimedItemCount`（未领取物品）。这两个字段就是权威的金额/数量，与税率（普通物品 4%、牛铃袋 18% 等）、取整规则完全无关，税率或规则变化都不影响本功能。
- **口径（v2.20.0 起）：订单在成交完成时就算收入/支出。**「未领取」只是拿到钱之前的**临时中间状态**——官方把成交结果写进未领取字段时，这笔交易就已经完成；玩家是否去点「收集」不影响订单的完成与金额。记录方式：每次观测到这两个字段**增加**（新成交，可多次部分成交）就把增量并入「累计到账」（`collectedCoinCount` / `collectedItemCount`）；字段**减少**（领取）不改金额，只补一条领取确认（时间 + 本次取走的金额明细）；登录快照对账发现条目消失（离线期间或在其他设备上领取）同样只补领取确认。
- **已终结订单的金额补齐**：官方数据可能不完整——典型是登录快照补齐的订单只带回剩余可领取值（此前已领取的部分官方不再下发）。此时把金额补齐到应得额（**只补不足、不覆盖官方值**；进行中的订单不补齐，因为官方数据还会继续来），详见 §4.6。
- **税费口径与「成交价与挂牌价不符」的判定（v2.20.0 起）**：官方按**单件**收税、每件向上取整——**税费 = ceil(单价 × 税率) × 已成交数量**，不是「总额 × 税率」的浮点值（2026-10-12 用 672 条导出里全部 385 条可倒算的出售记录逐条核对，全部吻合；按总额取整只对得上 303 条、按单件四舍五入 352 条）。因此由税费反推单价只能得到「单件税费档位」：单件税费为 k 时成交价落在 `((k − 1) ÷ 税率, k ÷ 税率]`，区间内任何价格产生的官方税费完全相同，区间宽度就是一个档位（4% 档 25 金币、5% 档 20、2% 档 50、牛铃袋 18% 档 5.56）。**「倒算值与挂牌价不同」不能说明价格移动过**——v2.20.0 开发中曾据此判定，凡是单价不是档位整数倍的记录都被误标星号、收入被算高（实测导出 82 条误标、合计多算 675,802），已修正为下面两个真正的「不符」条件：**① 单件税费不是整数**（各次成交的单价不同 → 成交价不止一个，不可能每次都按挂牌价成交）；**② 单件税费是整数但挂牌价落在证据区间之外**（成交价确实高于区间上限或低于下限）。判定用整数交叉相乘（`price × 分子` 对比 `档位 × 分母`），不走浮点除法；成交跨过税率调整日（普通物品 2026-08-14 前 2%、08-14 起 5%、09-28 起 4%）的记录税费混了两个档位、不做判定；牛铃袋 18% 一档跨日期照常判定；买入不扣税、不参与；时间缺失时同样放弃。证据允许的成交额（毛额）区间是 `((税费 − 数量) ÷ 税率, 税费 ÷ 税率]`；界面在这类记录「金额」列旁标 `*`，悬浮给出区间上下限与税率并说明「金额」列按挂牌价计算只作参考（`taxDerivedAmountOf` 只用于展示，`taxEvidenceOf` 是展示与金额共用的判定），**收入与金额补齐都取证据下限**（宁可少算也不虚增，官方到账更完整时以官方为准）。实测复核（同一份 672 条导出）：385 条可判定记录里符合「不符」条件的为 **0** 条，修复前会打星的 82 条全部是「单价不是档位整数倍」的误报，出售收入合计随之回落 675,802。
- 因此记录里保留的口径是：**名义成交额**（单价 × 已成交数量，参考）与**收入/支出**（卖出是税后全额/补齐、买入是支出金额），列表里分别叫「金额」与「收入/支出」，不再有独立的「待领取」显示（列表行、悬浮、CSV 与合计里都不出现）；金额含推算成分时在悬浮里标注（§4.6）。
- **旧数据迁移**：v2.19.0 及更早的记录里，「累计到账」只算已领取的部分——首次读取时把「官方仍未领取」的部分并入累计到账并写入 `unclaimedCounted` 标记，迁移幂等（标记随记录持久化，重复读取不会重复累计）；未领取值本身保留为与官方对账的增量基准，不参与展示。
- **重复投递 / 乱序的防护（v2.20.0 起）**：未领取值是一条「领取后归零」的临时值，重复投递、乱序到达或跨标签页旧口径合并都会让同一个旧值再次出现，照着差额入账会把同一笔成交记两次（实测样本 `listing:160465584`：出售 4 × 1,144,000 的收入被记成 8,785,920，正好是应得额 4,392,960 的两倍，且领取明细与剩余未领取也各是 4,392,960）。因此**正向增量只在「确实有新成交」时并入**：判定依据是已成交数量增加（有新成交时进度必然增加），此前没有任何入账（首次拿到官方凭据、推算金额刚被作废、直购这类「请求即完成」的订单）也不受限；**被拦下的旧值同时不写回基准**，否则下一次真实成交会拿被污染的旧值做差额，金额少记或错记。同一序列（成交 → 领取 → 旧值再次出现）按修复前的差额逻辑重放会得到两倍金额，新逻辑保持应得额（`tests/market-history.test.js` 的「重复出现的旧可领取值不再重复入账」用例固定了这一点）。

### 4.7 与「食用工具」的互通（桥接脚本）

- 油猴的 GM 存储按脚本隔离：MST 用 `GM_getValue('market_list')` 读不到食用工具的订单数据，食用工具也读不到 MST 的记录；实测确认食用工具把 `market_list` 只写自己的 GM 存储（localStorage 只有设置与市场价缓存、没有挂 window、没有导出功能）。
- 配套桥接脚本 `integrations/edible-tools/edible-tools-market-bridge.js` 通过食用工具脚本头的 `@require` 引入（`@require` 的代码运行在食用工具的沙箱里，因此能读写它的 `market_list`），在食用工具「银河奶牛数据库 → 市场数据」页的「仅保留已完成订单」按钮之后注入两个按钮（导出/导入统一为 MST 格式，只在食用工具之间做迁移也能用）：
  - **导出到 MST 交易记录**：把 `market_list` 转成 MST 导出格式下载（环境按导出时所在页面判定），MST 里用「导入」选择该文件即可；
  - **从 MST 交易记录导入**：读取 MST 导出的 JSON，按官方订单 id 合并回食用工具的存储（只接受这一种格式，食用工具的原始数组备份不再支持）。
- 字段映射以官方挂牌对象为准（`id`/`characterID`/`status`/`isSell`/`itemHrid`/`enhancementLevel`/`price`/`orderQuantity`/`filledQuantity`/`createdTimestamp`/`expirationTimestamp`/`taxTaken`/`unclaimed*`，已对照食用工具 v0.514 源码核对：它保存的就是官方对象原文加自己的 `lastUpdated`，收到官方更新时按 `id` 整条替换）；食用工具没有领取记录，导入 MST 时 `collected*` 与 `claims` 为空，MST 随即按 §4.6 对这类记录推算金额；MST 里没有官方订单 id 的直购/直售兜底记录无法表达，导入食用工具时跳过并计数。桥接脚本不参与 MST 构建，详细说明见该目录 README。
- **食用工具条目没有的 MST 信息**（环境、订单类型、推断标记）：桥接不写自定义字段，条目保持食用工具自身的结构（官方挂牌对象 + `lastUpdated`）——导出环境按所在页面判定，类型统一按挂牌处理，创建时间缺失时才标推断；跨环境记录与直购分类经食用工具中转后不保真（金额与状态不受影响），只在单环境使用时无影响。首次成交时间食用工具没有记录，有成交时用 `lastUpdated` 近似。
- **食用工具之间迁移**：导出只有「导出到 MST 交易记录」一种（MST 格式是唯一互通格式），另一台设备的食用工具用「导入到食用工具」读同一份文件即可；读文件后用 `prompt` 选择导入方式——1 = 合并（同订单终态优先、否则取更新时间较新，进度与税费取大，新订单追加）、2 = 覆盖（先清空现有数据再写入，带 confirm 二次确认）。按钮文案跟随食用工具自身的语言判定（读游戏 `localStorage.i18nextLng`，非 `en` 即中文），不依赖页面 html lang。

## 五、数据模型

### 5.1 记录结构

```js
{
  key: 'listing:123456',        // 主键（见 5.2）
  environment: 'live',          // live = 正式服（含 cn 镜像）；test = 测试服
  characterId: '1234',          // 角色 id（用户隔离的桶键）
  characterName: 'Sunrishe',    // 记录时角色名，便于导出后辨认
  originHost: 'milkywayidlecn.com', // 最近一次写入来源域名（诊断用，不参与隔离）
  kind: 'listing',              // listing = 挂牌；instant = 直购/直售
  side: 'sell',                 // sell = 出售（挂牌/立即出售）；buy = 购买（订单/立即购买）
  listingId: 123456,            // 官方订单 id；兜底路径的直购未关联时为空
  itemHrid: '/items/abyssal_essence',
  enhancementLevel: 0,
  price: 1200,                  // 单价（委托价）
  orderQuantity: 100,           // 挂牌/委托数量
  filledQuantity: 60,           // 已成交数量
  status: 'cancelled',          // 见 5.3
  createdAt: 1759200000000,     // 观测到的创建时间
  updatedAt: 1759203600000,     // 最近一次观测到变化的时间
  firstFillAt: 1759201000000,   // 首次成交时间（可空）
  filledAt: null,               // 全部成交时间（可空）
  cancelledAt: 1759203000000,   // 取消时间（可空）
  expiredAt: null,              // 过期时间（可空）
  claimRequestedAt: null,       // 领取请求时间（可空）
  claimedAt: null,              // 观测到领取完成的时间（可空）
  expiresAt: null,              // 官方过期时间（expirationTimestamp，可空）
  taxTaken: 0,                  // 官方累计税费（taxTaken）
  unclaimedItemCount: 0,        // 官方未领取物品数：只作增量对账基准，不参与展示
  unclaimedCoinCount: 0,        // 官方未领取金币数（已扣税）：同上
  unclaimedCounted: true,       // 该基准是否已并入累计到账（旧数据首次读取时迁移为 true）
  collectedCoinCount: 0,        // 累计收入金币（出售侧：成交完成即计入；信息不全的已完成订单按税率补齐，见 §4.6）
  collectedItemCount: 0,        // 累计收到的物品件数（购买侧：成交完成即计入）
  claims: [],                   // 领取确认明细 [{at, coinCount, itemCount}]，最多保留 20 条，不参与金额计算
  origin: 'update',             // 记录来源：snapshot | update | request | import
  inferredTime: false,          // 时间是否为推断（快照补齐 / 未观测结束）
  endedUnobserved: false,       // 是否属于「已结束（原因未观测）」
  importNote: ''                // 导入合并备注（冲突原因等，可空）
}
```

- 时间一律为本机毫秒时间戳，界面按本地时间 `yyyy-MM-dd HH:mm:ss` 显示。
- 金额为金币整数，界面按 K/M/B 缩写显示，悬浮显示精确值。
- 记录内不保存物品名称，显示时通过 `DataHub.resolveItemName` 解析（中英文随界面语言切换）。

### 5.2 记录主键与去重

| 类型         | 主键                                  | 去重规则                                                   |
| ------------ | ------------------------------------- | ---------------------------------------------------------- |
| 挂牌 / 直购  | `listing:<官方订单 id>`               | 官方 id 唯一，跨设备合并天然可靠（直购走主路径时同样适用） |
| 直购（兜底） | `instant:<本机生成>`（时间戳 + 随机） | 跨设备无法用 id 对齐，导入时按内容启发式去重（见 5.5）     |

分桶键为「`environment` + `characterId`」，同一用户的记录放在一起；`originHost` 只作诊断，不参与隔离。

### 5.3 状态映射

| 界面显示           | 判定                                                       | 说明                                                                                                                                      |
| ------------------ | ---------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| 有效               | `status='active'` 且 `filledQuantity=0`                    | 挂牌等待成交                                                                                                                              |
| 部分成交           | `status='active'` 且 `filledQuantity>0`                    | 仍有剩余数量在市场上                                                                                                                      |
| 已完成             | `status='filled'`                                          | 全部成交即完成（金额已计入），与是否领取无关                                                                                              |
| 部分成交后取消     | `status='cancelled'` 且 `filledQuantity>0`                 | 已成交部分保留，未成交部分退回                                                                                                            |
| 部分成交后过期     | `status='expired'` 且 `filledQuantity>0`                   | 同上，30 天到期                                                                                                                           |
| 已取消 / 已过期    | `status='cancelled'` / `'expired'` 且 `filledQuantity=0`   | 未产生任何成交                                                                                                                            |
| 立即成交           | `kind='instant'`                                           | 直购/直售，含委托价信息                                                                                                                   |
| 未确认             | `kind='instant'` 且 `listingId` 为空（没有关联到官方条目） | 直购/直售兜底记录：是否真的成交、成交价多少无法与官方核对（见 §4.5），可按状态筛选后人工处理；一旦关联上官方条目就写回 id、回到「已完成」 |
| 结束（原因未观测） | `endedUnobserved=true`                                     | 见 4.3 第 7 条                                                                                                                            |

「已完成」记录在 `claimedAt` 非空时在悬浮里显示领取确认（时间与金额明细）；领取不改变状态与金额。

### 5.4 推进规则（观测事件 → 记录）

- 每条观测事件只做字段级 upsert，不做覆盖式重写；`filledQuantity` 只增不减，`updatedAt` 取最新观测时间。
- 同一 id 从 Active 变为 Filled 时，写入 `filledAt`（若已有值则保留更早者）；`firstFillAt` 取首次 `filledQuantity>0` 的观测时间。
- Cancelled / Expired 同时写入对应时间（含「部分成交后取消/过期」）；`endedUnobserved` 在任何一次重新观测到该 id 条目时都清除（条目还在就说明没结束，不论观测到的状态是不是终态）。
- 领取确认：收到「未领取数归零」的同 id 条目、携带该 id 的领取请求（记 `claimRequestedAt`）、或随后的快照缺失时，补一条领取确认（`claims` 明细 + `claimedAt`），记录保留、状态与金额不变。
- **收入 / 支出计入**（§4.6，v2.20.0 起）：① 每次观测到 `unclaimedCoinCount` / `unclaimedItemCount` 比上一次记录的**基准值增加**时，把增量并入 `collectedCoinCount` / `collectedItemCount`——这是金额的唯一来源，**多次部分成交分别计入**（未领取合并时只计新增量）；正向增量还要求「确实有新成交」：已成交数量增加，或此前没有任何入账（首次拿到官方凭据、推算金额刚被作废、直购这类「请求即完成」的订单），否则视为重复投递的旧值、不并入也不写回基准（§4.6 的防护）；② 观测到**减少**（领取）时不改金额，只补领取确认；③ 条目从快照消失（离线期间或跨设备领取）时同样只补领取确认。旧记录（v2.19.0 及更早）首次读取时把未领取部分并入累计到账，`unclaimedCounted` 标记保证迁移幂等。两个未领取字段保留为增量基准，界面不展示。

### 5.5 合并规则（导入 / 多标签页 / 跨设备）

以主键为单位的字段级合并，规则如下（同时用于导入与多标签页同步）：

| 字段                                                                   | 合并规则                                                                                                     |
| ---------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| `status`                                                               | 终态优先：filled/cancelled/expired 优先于 active；两个终态不同时取变更时间较晚者，并记 `importNote` 冲突备注 |
| `filledQuantity`                                                       | 取较大值（单调不减）                                                                                         |
| `orderQuantity` / `price` / `itemHrid` / `side` / `enhancementLevel`   | 取 `updatedAt` 较晚的记录（内容不一致时记冲突备注）                                                          |
| `createdAt`                                                            | 取较早的非空值                                                                                               |
| `expiresAt`                                                            | 取较早的非空值（官方过期时间恒定，任一侧有值即可）                                                           |
| `taxTaken`                                                             | 取较大值（税费随成交累加，单调不减）                                                                         |
| `firstFillAt` / `filledAt` / `cancelledAt` / `expiredAt` / `claimedAt` | 取较早的非空值（不同设备观测同一事件，早者更接近真实时间）                                                   |
| `unclaimedItemCount` / `unclaimedCoinCount`                            | 取 `updatedAt` 较晚的记录（只作对账基准，不展示）                                                            |
| `unclaimedCounted`                                                     | 恒为 true（两侧归一化读取时都已迁移并入累计到账）                                                            |
| `collectedCoinCount` / `collectedItemCount`                            | 取较大值（累计量单调不减，跨设备两边各自累加的部分不会互相覆盖）                                             |
| `claims`                                                               | 领取确认明细，按时间合并去重，最多保留 20 条                                                                 |
| `updatedAt`                                                            | 取较大值                                                                                                     |
| `endedUnobserved`                                                      | 观测到该条目即清除（终态或仍是有效状态都算「还在」），否则保留                                               |

**直购兜底记录的内容去重**（跨设备）：同 `environment` + `characterId` + `side` + `itemHrid` + `enhancementLevel` + `orderQuantity` + `price`，且 `createdAt` 相差 ≤ 10 分钟 → 视为同一笔，保留较早时间并合并；无法确认时宁可保留两条（在导入报告中提示「疑似重复 N 条」）。

### 5.6 部分成交后取消 / 过期（专项口径）

- 记录同时保留：`filledQuantity`（已成交数量）、`firstFillAt`（首次成交时间）、`cancelledAt` / `expiredAt`（终态时间）。
- 列表状态列显示「部分成交后取消（3/10）」，进度列显示已成交/总数；悬浮显示取消时间与未成交退回说明。
- 统计只按已成交数量与金额计入，未成交部分不计；「部分成交后取消」在状态筛选中可单独选择。
- 合并（导入/多设备）时，终态与已成交进度各自按 §5.5 规则处理，不会因取消而丢掉成交记录。

## 六、存储方案

- 存储键：`MST_MARKET_history`（新增到 `src/common/data.js` 的 `STORAGE_KEYS`，格式沿用 `MST_简短模块名_key`）。
- 存储内容：`{schemaVersion: 1, updatedAt, buckets: { '<environment>:<characterId>': [records...] }}` 的 JSON 字符串，记录按主键排序保存，便于人工核对。
- 写入策略：内存态为唯一工作副本，变化后 500ms 防抖写一次；`pagehide` / `visibilitychange(hidden)` 时立即冲写，减少关页面丢数据的窗口。
- 跨标签页：`GmApi.addValueChangeListener` 监听自身键，收到外部变更时按主键合并进内存（不弹提示），避免两个标签页互相覆盖。
- 容量：记录数 > 20000 或 JSON 体积 > 4 MB 时在弹窗顶部提示「记录过多，建议导出后清理」，**不自动删除**；存储写失败（配额不足）时 Toast 提示并保留内存数据。
- 数据迁移：`schemaVersion` 不匹配且无法升级时，提示用户先导出备份，不静默丢弃。

## 七、功能定义

### 7.1 入口

1. **市场标签栏按钮**：「交易记录」按钮与「商品列表 / 我的挂牌」两个主标签**并排**，位于同一标签栏内、排在标签之后（右侧），不放进标签内容区（不是「全部收集」那一行，也不是面板内部其他位置）。
   - 挂载点：市场面板的主标签栏容器内（目标为 `MarketplacePanel_marketplacePanel__` 下的 `.MuiTabs-flexContainer`，与 MUI 标签同排），把按钮追加到标签行末尾；面板被 React 重渲染清掉后由公共 DOM 观察器重建。
   - 标签栏常驻，切换到「商品列表」或「我的挂牌」都能看到该按钮；语言切换时更新按钮文案；样式复用游戏 MUI 主标签的 `MuiButtonBase-root` / `MuiTab-root` 类，并在旧层级回退时用模块 CSS 对齐同尺寸、圆角、底色、悬停色与前景色；文字和 SVG 图标统一使用标签前景色。
2. **工具箱菜单入口**：在工具箱下拉菜单中新增一项「市场交易记录」（`src/modules/toolkit-menu/index.js` 的 `getActions()`），点击调用与上面按钮**同一个** `open()` 方法。
3. 两处入口都在游戏站初始化；模块单例标记防止重复实例。

### 7.2 弹窗

- 使用 `Notifier.html`，宽度取 `min(76rem, calc(100vw - 1rem))`，高度铺满可用视口（`max-height: calc(100dvh - 2rem)`），内容区独立滚动；表格区域横向必要时可横向滚动，窄屏下工具栏换行。
- 弹窗内分四个标签页：
  1. **记录**：一行筛选栏（关键词、分类、状态、类型、时间范围、「更多」开关、「清除」、批量删除），时间范围下拉默认项即「创建时间」（固定按创建时间筛，无独立标签，选项与统计页签同一套）；单价与数量收进「更多」按需展开（折叠时开关上以角标显示生效条件数）；记录表（表头固定，表格内不放合计行）；底栏（上方为「本页合计 / 筛选总计」两个合计分组，宽度允许时同行、放不下时换行；下方一行是总条数与右侧紧挨着排列的跳页输入、每页条数下拉与翻页按钮组，中间不再留白）。
  2. **统计**：独立筛选栏 + 总览数值卡 + 四张图表（收支趋势 / 物品排行 / 分类构成 / 记录构成）+ 按物品汇总表（见 §7.6）。
  3. **管理**：导入、导出与数据修复三块（导入 / 导出为原工具栏按钮移入，数据修复见 §7.12）。
  4. **帮助**：食用工具桥接脚本的接入与双向迁移步骤（见 §7.11）。
- 弹窗打开期间语言切换：整体重绘（沿用订阅通知的做法），筛选条件与页码保持在内存中。

### 7.3 列表与列

默认列：复选框（勾选行，配合批量删除）、序号（筛选排序后的行号，跨页连续）、状态、类型、物品（图标 + 名称 + 强化等级）、进度（已成交/总数）、单价、金额（单价 × 已成交数量）、收入/支出（卖出是税后收入、买入是支出金额；有官方到账数据时以官方为准）、创建时间、完成时间、操作（单条删除）。
可选操作：点击列头排序；悬浮「完成时间」显示各阶段时间（首次成交、完成、取消/过期、领取）；悬浮「收入/支出」显示领取确认明细（每次领取的时间与金额）、**精确原值**、本单税费与推算说明，推算记录还会标注所用税率；表格里所有缩写过的数字（单价、金额、成交数量、底栏合计与统计页签的金额）都在 `title` 里给出带千分位的精确值。

- 列表采用固定列宽（`table-layout: fixed`，宽度写在表头）：勾选态、确认删除等行内内容变化不得重算列宽导致整表抖动；超长内容以省略号截断并用 `title` 提供全文。**每一列都必须写宽度**（含「物品」列）：固定布局下没有宽度的列在容器变窄时会被压成 0 宽度、整列消失；表格同时声明最小宽度（= 列宽合计，72rem），容器比它窄时由表格区域（`.mst-market-history-table-wrap`，`overflow: auto`）横向滚动，不压缩任何一列。
- 进度列在已成交与总数一致时只显示一个数字，不等时显示「已成交 / 总数」；直购按购买数量显示。
- 「单价」列按游戏市场的价格写法显示（`utils.formatMarketplacePrice`，与订单簿、挂牌页速览一致：10 万以下整数不带千分位，10 万 / 1000 万 / 100 亿 / 10 万亿起换算 K / M / B / T，换算后不足 100 保留两位、不足 1000 保留一位、再大取整）；统计页「按物品汇总」的「加权均价」同样是价格，用同一种写法；「金额」「收入/支出」等金额列仍用紧凑写法（`formatCompactNumber`，两位小数），两类写法各自服务「价格」与「金额」的语义。
- 数字列（序号、进度、单价、金额、收入/支出）右对齐并启用等宽数字；零值与空值（`0`、`—`）弱化显示，避免与真实数值抢注意力；「收入/支出」按方向着色（收入用正向色 `--color-jade-300`、支出用负向色 `--color-scarlet-300`，与装备对比的涨跌配色一致，0 不上色）。
- 时间列使用表格短格式（当年省略年份，跨年省略时间），完整时间放在 `title`；悬浮与导出仍用完整格式。
- 单条删除是行尾方形 × 按钮，尺寸与配色必须与战斗升级计算器列表的删除按钮一致（1.45rem × 1.55rem、`#9a5d66` 描边、`#f4c4ca` 前景、midnight-400 底、0.25rem 圆角）；第一次点击进入确认态（警示填充 + 「确认删除」提示），第二次点击才删除，确认态不改变列宽。
- 行悬停高亮；勾选的行常亮，表头复选框支持「全选本页」与半选态。
- 物品图标取 `SpriteService` 的 items 精灵图（`utils.getSpriteUrl('items')`），与装备对比、地下城收益一致。
- 空态：无记录时显示「暂无记录，市场交易后自动记录」；筛选无结果时显示「没有符合条件的记录」。

### 7.5 排序

- 可排序列：创建时间（默认，倒序）、完成时间、单价、成交数量、金额、收入/支出、物品名、状态（类型与操作列不可排序）。列键必须与排序实现支持的键一致（如成交数量用 `filledQuantity`）。
- 点击列头切换升/降序，当前排序列显示箭头；排序与筛选可叠加；排序稳定（同值按创建时间倒序兜底）。工具栏不另设排序控件（屏幕空间留给筛选与操作）。

### 7.6 分页与统计（全做）

- 每页条数：20（默认）/ 50 / 100 / 200 / 500 / 1000，下拉选项文案为「20 条 / 50 条 / …」（英文「20 rows / …」），不另外显示「每页」标签。
- 合计（本页合计 / 筛选总计）放在**弹窗底栏、分页区上方**：每个分组是「标签 + 数值」的紧凑串（成交数量、收入金额「金额 / 收入金额」、支出金额只显示一个金额，**不含条数**——条数由底栏「共 N 条」承担），标签弱化、数值加粗；两个分组在宽度允许时同一行，放不下时自动换行。表格内不放合计行，也不做锁定行。
- 底栏最左显示总条数（「共 N 条」），右侧依次为跳页输入（文案「第 __ 页」）、每页条数下拉与翻页按钮组（上一页 / 页码 / 下一页），三者紧挨着排列、中间不留额外空白；宽度不足时允许换行。
- 页码按钮最多 5 个：两端固定 + 当前页附近窗口，其余用省略号（如 `1 … 14 15 16 … 34`）。
- 跳页输入接受 1 至页数之间的整数，越界收敛；回车或失焦生效。
- 记录页签合计口径（本页与当前筛选结果总计同时给出）：
  - 条数、委托数量合计、已成交数量合计；
  - **收入金额**按「金额 / 收入金额」并列（出售侧：卖出总额 / 成交即计入的税后收入），**支出金额**不扣税、只显示一个数（购买侧：数量 × 单价）；待领取不再是独立口径，不参与合计。
  - 金额（单价 × **已成交数量**，部分成交后取消只计已成交部分）作为出售/购买两侧的原始金额；直购兜底记录（无官方条目）没有官方到账数据时用推算金额并标注。
- **统计**标签页（随 v2.19.0 交付）：
  - **筛选条件与记录页签完全独立**（不复用列表筛选，也不再提供「统计全部记录」开关）：时间范围（与记录页签同一套：创建时间（默认）/ 近 7 天 / 近 15 天 / 近 30 天 / 近 60 天 / 近 90 天 / 近 180 天 / 自定义起止）、方向（全部 / 出售 / 购买）、分类（与官方市场分类一致）、物品关键词（匹配中英文名与 hrid），另有一键清除；时间口径统一按**创建时间**（`record.createdAt`），筛选与趋势图分桶同源，下拉默认项即「创建时间」以免与完成时间混淆（不再另加标签）。筛选值经 `filterRecords`（新增 `sides` 入参，`timeField` 保持默认的创建时间）执行，取数结果按数据签名缓存。
  - 总览数值卡：笔数、成交数量、**收入金额**（出售侧的税后收入 / 受约束推算）、**支出金额**（购买侧数量 × 单价，不扣税）与**净收支**（收入 − 支出，正数绿、负数红、0 不上色）；待领取不再是独立口径（金额在成交完成时计入，见 §4.6），也不再单列委托数量与出售 / 购买金额。
  - **四个维度的图表**（全部手绘 SVG + HTML 条，不引图表库；几何计算集中在 `charts.js`，可单测）：
    1. **收支趋势**：按创建时间分桶的收支柱（收入 / 支出）+ 净收支折线；粒度可切自动 / 日 / 周 / 月（默认自动：跨度 ≤ 45 天按日、≤ 400 天按周、更大按月；周从周一起算、月从 1 号起算）；空桶保留以便看到断档；桶数超过 120 时自动升档并在卡片内提示「数据跨度较大，已按 X 聚合」；净收支为负时纵轴包含负值并画出零线；某方向全为 0 时不画该系列。
    2. **物品排行**：按指标取前 10 名（金额 / 数量 / 笔数可切换），每条是出售（绿）+ 购买（红）的堆叠横条，条长按最大值归一。
    3. **分类构成**：环形图，可在支出（购买金额）与收入（出售到账 / 推算）之间切换，图例给出紧凑数值与占比。
    4. **记录构成**：环形图，可在状态与类型之间切换，占比按条数。
  - 图表交互：扇区 / 柱子 / 排行条 / 图例 / 数值卡都带悬浮提示，数字给出带千分位的精确原值；无数据时卡片内显示「当前筛选没有可统计的数据」，整个筛选结果为空时显示「没有符合条件的记录」（筛选栏保留在顶部，便于放宽条件）。
  - **按物品汇总表**：每个物品（含强化等级）的条数、成交数量、加权平均单价、**出售金额**、**购买金额**与收入金额（出售与购买分列，收尾口径与总览一致），按金额合计倒序；表格在固定高度内滚动、表头吸顶，避免把上方图表顶出视野。
  - **实现约束**（都是实测踩过的坑，改图表时必须守住）：① `charts.js` 只做纯几何计算（轴刻度、分组柱、堆叠条、环形弧），不碰 DOM、不引图表库，界面侧用 uhtml 标记组装；② **SVG 片段必须用 uhtml 的 `svg` 标记**——`html` 标记生成的元素带 HTML 命名空间，插进 `<svg>` 后不显示且控制台不报错（柱子、折线、扇区曾整块消失，只能靠截图发现）；③ uhtml 的数组插值不接受 `null` / `undefined` 元素（数组位会抛 `Cannot read properties of null`，整块内容渲染中断），条件渲染用空模板、条件数组退回 `[]`，数组插值只收集命中的模板（`templateList`）；④ 空数据卡片保留维度切换按钮，否则用户无法从「当前指标无数据」切到另一个指标；⑤ 自动粒度与请求粒度分开记录（`bucket` / `expectedBucket`），只有实际粒度真被升档时才提示用户。
- 说明：**实时链路的到账一律以官方数据为准**（官方 `unclaimedCoinCount` / `unclaimedItemCount` 的减少量累计），不按税率估算；「金额」是单价 × 已成交数量的原始金额。
- **已完成订单的金额补齐（v2.20.0 起）**：**只对已终结的订单**（已完成 / 已取消 / 已过期 / 结束未观测）生效——进行中的订单官方数据还会继续来，只记已经观测到的金额、不推算，避免与后续增量重复。官方金额（成交时按可领取值增量累计的部分）**不足应得额**时按成交当时的税率补齐并在悬浮提示里标注；**只补不足、不覆盖官方值**（官方累计达到或超过应得额时原样保留，对手方以更优价成交时官方到账会高于按挂牌价的推算值）。典型场景：登录快照补齐的订单只带回剩余可领取值，此前已领取的部分无从得知 → 按应得额补齐。**只有出售扣市场税**：出售 = 已成交数量 × 单价 ×（1 − 成交当时税率），税率档位为普通物品 2026-08-14 前 2%、2026-08-14 起 5%、2026-09-28 起 4%，牛铃袋（`/items/bag_of_10_cowbells`）始终 18%；**购买不扣税**：购买 = 已成交数量 × 单价。补齐结果一律记 `collectedCoinCount`（金额），绝不在列表里显示裸件数；完全没有官方线索的纯推算记录每次归一化按最新公式重算（公式调整后能自动纠正），带官方线索的记录只补差额，加载与导入时各跑一次。
- 导入备注（`importNote`）在归一化时按「；」分段去重：旧版本曾无上限追加同一段备注，实测出现过单条 501KB、同一句重复 3 万多段的脏数据，读取时收敛为唯一分段。

### 7.7 批量删除

- 列表每行与表头都有复选框；**批量删除只处理勾选的行**，勾选跨页保留、打开弹窗时清空。
- 批量删除按钮放在筛选栏「清除筛选」之后；有勾选时显示条数（如「批量删除 (3)」），无勾选时禁用。
- 删除是两次点击确认：第一次按钮切成「确认删除 N 条」，第二次才执行；执行后清空勾选、Toast 提示删除条数。
- 删除不可撤销，界面保留「建议先导出备份」的提示（导出见 §7.8）。
- 删除只作用于**当前用户（当前环境 + 角色）**的本地记录。

### 7.8 导入导出

- **导出**（只针对本人数据）
  - 范围：当前角色（默认）/ 全部角色；
  - 格式：JSON（`{app: 'MST', type: 'market-history', schemaVersion, exportedAt, buckets: {...}}`），**紧凑输出（不带缩进）**，导入端只做 `JSON.parse`，与格式化文件完全互通。
  - 文件名：`MWI市场交易记录_<角色名或all>_<yyyyMMdd-HHmmss>.json`；下载方式与房屋计算器 CSV 导出一致（Blob + `a[download]`）。
  - 另提供 CSV 导出（只导出当前筛选结果，供表格工具查看，不支持导入）。
- **导入**
  - 来源：选择 `.json` 文件或粘贴文本；
  - **导入内容不跨次保留（v2.20.0 起）**：关闭弹窗即清空导入文本、文件名、导入模式、覆盖确认、预览结果与错误提示（打开弹窗时也先重置一次）；文件异步读取的回调在弹窗关闭后直接丢弃结果。避免整份导出文件的大文本在下次打开时重新渲染造成卡顿；
  - 校验：格式、`schemaVersion`、逐条字段合法性；非法条目计入「跳过」；
  - 模式：**合并**（默认）/ **覆盖**；
    - 合并：按 §5.5 规则并入现有记录（覆盖已存在主键的字段、追加新主键）；
    - 覆盖：仅覆盖文件中出现的「环境 + 角色」分桶，其他分桶不动；执行前二次确认（提示将删除对应分桶现有记录）；
  - 预览与报告：新增 / 更新 / 内容去重（直购兜底记录）/ 跳过 / 冲突（状态不一致）条数，执行后显示同样口径的报告；冲突条目可在列表中通过状态列悬浮查看备注。
  - 场景覆盖：设备 A 挂单、设备 B 成交 → 两边导出合并后得到一条「创建时间来自 A、完成时间来自 B」的完整记录；离线完成的订单在登录快照中按订单 id 合并。

### 7.9 提示与错误

- 记录写入失败（GM 存储不可用 / 配额）：Toast 警告，功能仍可查看内存数据。
- 导入失败：Toast + 具体原因（格式错误 / 版本不支持 / 无有效记录）。
- 面板按钮注入失败：静默重试（公共 DOM 观察器），不打断游戏。

### 7.10 i18n 与样式

- 文案统一放 `src/common/messages.js` 的新分组 `MARKET_HISTORY_MESSAGES`，中英双语，无散落硬编码。
- 模块私有样式 `src/modules/market-history/styles.css`，类名 `mst-market-history-` 前缀；动态数值只透出 CSS Variables；弹窗层级沿用 `--mst-z-popup` 约定。

### 7.11 帮助页签

说明食用工具桥接脚本怎么接、数据怎么两边走，用户不用翻仓库文档：

- **食用工具 → 交易记录**：① 在油猴里给食用工具的脚本头加一行 `@require`（脚本头代码块 + 「复制这一行」按钮，`utils.writeClipboard` 写入后 toast）；② 食用工具设置面板 → 银河奶牛数据库 → 市场数据 → 「导出到 MST 交易记录」；③ 本弹窗「管理」页签导入该文件。补充说明：导入的记录带「来源：食用工具」备注、「收入/支出」按成交当时税率推算并标注（出售扣税、购买不扣税）、无官方订单 id 的兜底记录会被跳过。
- **交易记录 → 食用工具**：① 同上接入脚本；② 「管理」页签导出 JSON；③ 食用工具「市场数据」页 → 「导入到食用工具」，prompt 里选 1 合并 / 2 覆盖（覆盖会清空食用工具现有全部订单、含其它角色，不可撤销）。
- **多台设备之间迁移**：一份文件两边通用（同为 `{app:'MST', type:'market-history'}`），MST 与 MST 之间直接导出导入即可，不需要桥接脚本。
- **注意事项**：桥接脚本只处理市场订单数据；只有 MST 自己观测到的官方到账才是权威值；食用工具存储不分正式服/测试服，跨环境分开导出；覆盖式操作不可撤销，先导出留底。
- `@require` 行固定到已发布提交（`EDIBLE_BRIDGE_PINNED_COMMIT`，jsDelivr `@<commit>` 写法），保证用户拿到的桥接脚本与文档描述一致；食用工具自身更新脚本后需重新加该行。

### 7.12 数据修复（「管理」页签第三块，v2.20.0 起）

历史版本、跨设备导入与手工数据可能留下结构上不一致的记录。这些记录只读扫描出条数，用户勾选类型后一次性修复（`store.js` 的 `REPAIR_TYPE_KEYS` / `createRepairReport` / `scanRepairIssues` / `scanStoreRepairs` / `repairRecords`，`index.js` 的 `repairFormTemplate` / `repairCounts` / `applyRepair`）：

| 类型（`REPAIR_TYPE_KEYS`） | 判定（问题数据）                                                                                                                                                                                                                                                                                                                          | 修复方式                                                                                                                                                                   |
| -------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `duplicateListings`        | 同一角色桶里同一官方订单 id 有多条记录（跨设备导入、早期版本的直购关联路径留下）                                                                                                                                                                                                                                                          | 按 §5.5 合并为一条，主键统一为官方 id 键；直购记录保留直购语义                                                                                                             |
| `statusQuantity`           | 官方状态与成交进度矛盾：`filled` 但成交数量不足；进度已满却仍是 `active`                                                                                                                                                                                                                                                                  | 按官方状态修正（`filled` 的数量补齐为订单数量、补成交时间；进度已满的按已完成收尾），金额随后按 §4.6 补齐                                                                  |
| `unobservedEnded`          | 状态仍是「有效」，但官方登录快照（本会话拿到的 `myMarketListings`）里已经没有这单，且快照之后没再观测过                                                                                                                                                                                                                                   | 标记「结束（原因未观测）」并把时间标为推断，金额随后按 §4.6 补齐（与登录快照对账 `reconcileWithSnapshot` 同一口径）                                                        |
| `collectedFields`          | 到账字段与交易方向不符（出售带物品到账、购买带来源不明的金币到账、购买带税率）；出售被官方凭据完全解释的金额却还挂着推算标记；出售推算税率缺失或与成交时间档位不符                                                                                                                                                                        | 清除方向不符的累计值与多余标记、按成交时间补正税率；归一化时按当前口径重新整理                                                                                             |
| `amountRecalc`             | 已终结订单的累计到账与应得额（§4.6 的公式）不符：**购买侧口径就是「数量 × 单价」，有任何出入都算错**；**出售侧收入与「数量 × 单价 ×（1 − 税率）」差超过一半或 1000 金币**才算错（官方到账受价格带调整、以更优价成交影响，阈值内保留）。成因是旧版本公式、跨版本合并或手工数据（实测样本：同一笔成交被累计两次，金额正好是应得额的整数倍） | 按公式重算覆盖：出售 = 数量 × 单价 ×（1 − 成交时间税率），购买 = 数量 × 单价（不扣税），结果记 `collectedEstimated` 与所用税率；算不出应得额（数量或单价为 0）的记录不参与 |
| `settleEvidence`           | 累计到账既没有推算标记、又超过「领取明细之和 + 剩余未领取」（领取明细丢失或旧版本直接写下的金额）                                                                                                                                                                                                                                         | 按差额补一条结清明细（金额本身不变）；领取明细已记满 20 条上限的记录不参与，避免把正常截断当成缺凭据                                                                       |
| `unknownKey`               | 键不是 `listing:` / `instant:` 前缀的记录（早期测试与手工数据，无法与官方订单对应）                                                                                                                                                                                                                                                       | 删除                                                                                                                                                                       |

- 修复顺序：删除无法识别的键 → 合并重复订单 → 状态与进度 → 不在挂单列表 → 到账字段 → 金额重算 → 结清明细。后面的判定要看到前面修正后的状态（快照里没有的「进度已满」记录先按已完成收尾，就不再算作「结束原因未观测」）。
- `unobservedEnded` 只用「快照之后没再观测过」（`updatedAt ≤ 快照时间`）的记录判断：快照之后观测过或新建的记录快照给不出结论，留给下一次登录的快照对账；进度已满的记录归 `statusQuantity`；**没有拿到过登录快照的分桶（例如其他角色）这一类恒为 0**，不猜测。
- `amountRecalc` 与 `settleEvidence`、`collectedFields` 在同一字段上互斥：会写金额字段的分支（出售的推算标记 / 购买的金币残值）在 `amountRecalc` 命中的记录上让位给金额重算，避免两边都改导致报告与实际改动条数对不上；购买侧的物品账与金额是两条独立账，不互斥。
- 界面：复选框逐类勾选并显示条数，本机没有该类问题的复选框置灰不可勾选；「修复选中项」只处理勾中的类型，修复后按类型给出改动条数（合并 N 组 / 修正 N 条 / 删除 N 条），关闭弹窗即清空勾选与报告（与导入状态一致）；提示语写明修复前建议先导出备份。
- 扫描与修复共用同一套判定函数，界面显示的条数就是修复时实际改动的条数；修复是纯函数（不改动入参数组与记录对象），修复结果写回后重新扫描为 0（幂等），并能正常持久化回读。
- 不做自动修复：修复会改动本机记录（`unknownKey` 还会删除记录），全部由用户勾选后手动触发。

### 7.13 物品挂牌页速览（挂牌按钮上方的最近两次成交单价，v2.20.0 起）

市场里点开某个物品后的挂牌页（订单簿视图：「+ 新出售挂牌 / + 新购买挂牌」按钮行 + 下方左右两张订单簿），在按钮行的左端与右端各显示该物品该强化等级下**最近两条成交的单价**（按创建时间从新到旧，最近的一条在前、第二条是紧挨着的一条；只显示价格、不带文字标签）：

- 取值：当前「环境 + 角色」分桶里 `itemHrid` 与 `enhancementLevel` 都相同的记录，按方向（出售 / 收购）各取 `createdAt` 最新的两条；**已成交数量为 0 的不算**（取消 / 进行中的空单不是成交），**取消的订单也不算**（哪怕取消前成交过一部分，用户口径）；立即购买 / 立即出售兜底记录同样按方向参与；只有一条时只显示一个价格。
- 展示：左端（出售）显示最近两条出售单价、右端（收购）显示最近两条收购单价，**只显示单价、没有文字标签**；价格用游戏市场的写法（对照游戏源码 `formatMarketplacePrice`：10 万以下整数不带千分位，10 万 / 1000 万 / 100 亿 / 10 万亿起分别换 K / M / B / T，换算后不足 100 保留两位、不足 1000 保留一位、再大取整——与订单簿里的「出售价 / 收购价」显示一致，MST 侧实现为 `utils.formatMarketplacePrice`）；悬浮给出该条的类型、单价 × 成交数量、金额（精确原值）与创建时间，推断时间 / 未确认等备注照常带上；某一侧没有记录时该侧不显示。悬浮里的「金额」仍按列表口径（单价 × 已成交数量），不显示税后到账。
- 定位：挂牌按钮行（`MarketplacePanel_newListingButtonsContainer__`，游戏里 `display: flex; justify-content: space-between`）由模块样式设为 `position: relative` 锚点，两侧提示条 `position: absolute; top: 0` 分别贴左 / 贴右——不参与按钮行的 flex 布局。行内用 `padding-top: 1.05rem` 预留出上方的一条空白带放提示条：不留空间时提示条会落到父级订单簿容器（`MarketplacePanel_orderBook__`，`overflow: auto`）之外，**在页面上看不到**（实测 `elementFromPoint` 命中的是上方信息行而不是提示条）；预留带里不放其他内容，按钮仍贴行底，整体排版只多出这一条窄带。
- 视图判据与同步：物品与强化等级从游戏 `MarketplacePanel` 的 React state 读取（`marketListingsView / itemHrid / enhancementLevel`，读取器 `readMarketplacePanelState` 放在 `src/common/data.js`，与市场加购共用）；订单簿容器（`GameUiAdapter.selectors.marketOrderBooks`）既能定位 state、也作为「当前是订单簿视图」的判据（物品摘要视图同样有挂牌按钮行，但那里不显示速览）；页面观察器（DOM 变动）、记录变化（`scheduleSave`）与弹窗刷新路径（语言切换、其他标签页合并）都触发同步；渲染签名（物品 + 等级 + 语言 + 两侧记录的键与单价）不变且节点仍在文档里时不重建，离开订单簿视图或游戏重渲染清掉节点后由观察器补回。
- 边界：不请求官方接口、不改动游戏行为；订单簿本体由游戏加载，本模块只读取已渲染的按钮行并在其上绝对定位提示条。

## 九、评审意见与确认结果

### 9.1 已确认口径（2026-10-01 评审）

1. **环境只有正式服与测试服**：cn（`milkywayidlecn.com`）是官方中国镜像入口，与 `.com` 同属正式服；记录按「环境 + 角色」隔离。
2. **数据完全按用户隔离**：只在本地保存当前用户自己的记录，导入导出只处理本人数据。
3. **直购按订单 id 记录**：若服务端给直购分配订单 id，则完全按挂牌同一套逻辑以 id 记录；开发时先实测确认（§4.5）。
4. **离线不记录**：离线完成的订单在登录/收集时按订单 id 合并；离线取消/过期按「结束（原因未观测）」兜底。
5. **部分成交后取消单独处理**：保留成交进度与终态，统计只计已成交部分（§5.6）。
6. **入口按钮**：与「商品列表 / 我的挂牌」两个主标签并排，位于标签栏内（标签之后），不放进标签内容区、也不与「全部收集」同排。
7. **删除与统计功能全做**：单条 / 按物品 / 按单价 / 按筛选 / 清空全部；本页合计 + 总计 + 按物品汇总统计（§7.6、§7.7）。
8. **金额以官方数据为准**：收入/支出由官方 `unclaimedCoinCount` / `unclaimedItemCount` 的**增加量**累计，**订单在成交完成时即计入（v2.20.0 起，见 §4.6）**——待领取只是临时中间状态，不单独展示；不使用税率常量估算「预计到账」；仅对缺少任何官方到账线索的归档记录（典型是导入的历史数据）按成交当时的历史税率推算金额并标注（§4.6）：出售扣税、购买不扣税。
9. 其余按初版推荐执行：观测时间口径（含推断标记）、不提供「暂停记录」开关、筛选条件不持久化、每页默认 20 条、记录领取时间与取消请求时间、失败提示与容量阈值策略。

### 9.2 开发时验证 / 可再调整的项

1. **直购的服务端行为**：实测是否存在带 id 的订单条目；实测结果决定直购走主路径还是兜底路径（两者都已设计，切换不改变界面）。

### 11.3 未覆盖风险（交付时明确记录）

- 离线期间被取消/过期的记录无法确定具体原因（设计约束，按「结束（未知）」兜底）；
- 成交即入账（v2.20.0）依赖官方「可领取值」的出现与增量：成交期间页面关闭时，金额在下次登录快照里补入（时间取对账时刻）；跨设备（另一台设备上成交、本机只看到快照）同样以快照时间计入；
- 领取确认（`claims` 明细与 `claimedAt`）是参考信息：领取请求与归零条目都可能在脚本就绪窗口内丢失，丢失时金额不受影响（已在成交时计入）；
- 旧数据迁移只在首次读取新版本时执行一次（`unclaimedCounted` 标记随记录持久化）；迁移后记录里的未领取基准保留原值仅供对账，界面不展示；
- 金额补齐按「成交时间」取税率档位（`filledAt` / `firstFillAt` / `createdAt` 依次取）：快照补齐的订单成交时间取观测时间，跨税率调整日的极端情况下档位可能与实际略有出入；官方金额达到应得额时不受影响（不补齐）；补齐只补不足，官方后续给出更高金额时以官方为准；
